## Résumé de l'article

gopgext est un outil qui génère des extensions PostgreSQL à partir de code Go. Il transforme des fonctions Go annotées avec des commentaires spéciaux en fonctions SQL, en générant automatiquement le code C, les scripts d'installation et les fichiers de configuration nécessaires.

- Les projets sont du code Go standard, avec accès à la plupart de la stdlib (fmt, regexp, encoding/json, crypto, génériques, itérateurs, etc.)
- Les types Go (chaînes, nombres, tableaux, NULL, sets, lignes, timestamps, UUID, JSON) se mappent automatiquement aux types SQL
- Les extensions prennent en charge les fonctions, triggers, agrégats et index operators (GiST, GIN, SP-GiST, BRIN), ainsi que les foreign data wrappers
- Plusieurs extensions Go coexistent dans un même backend sans risque d'interférence
- Des ports de modules contrib PostgreSQL (pgcrypto, hstore, pg_stat_statements, cube) ont réussi les tests de régression en amont

## Discussion sur Hacker News (33 commentaires)

**Avis positifs** :
- Les extensions Postgres en Go offrent une alternative intéressante pour les équipes maîtrisant bien Go, particulièrement avec TinyGo qui résout les conflits de runtime en générant un binaire C simple-threadé compatible avec le modèle de processus de Postgres.
- L'utilisation de Go pour les extensions Postgres est un gain pour l'écosystème, ouvrant la porte à plus d'adoptants et d'extensions.
- Les gestion des erreurs en Go est judicieuse puisque les erreurs ne sont remontées qu'après le retour de Go, évitant les `longjmp` à travers la pile Go.
- Rust/pgrx et d'autres alternatives (plv8, pljs) offrent des options complémentaires : Rust a zéro runtime et intègre directement palloc, tandis que JavaScript offre flexibilité pour les opérations moins critiques en CPU.

**Avis négatifs** :
- Les frictions de runtime sont substantielles : conflits avec les handlers de signaux Postgres (SIGINT, SIGTERM, SIGUSR1), incompatibilités entre les contextes mémoire Postgres (palloc, CurrentMemoryContext) et le GC de Go, risquant deadlocks ou fuites mémoire en cas de panique ou annulation de requête.
- L'overhead de démarrage est problématique : chaque fork de processus Postgres doit initialiser la runtime Go, ses threads GC et le scheduler, ce qui peut augmenter significativement la mémoire et la latence sous haute concurrence.
- Go brille aux niveaux "plateforme" (Kubernetes, proxies réseau) mais semble moins adapté que d'autres pour les extensions au niveau du plan de données Postgres.
- Le modèle process-per-connection de Postgres crée une explosion mémoire potentielle avec plusieurs centaines de connexions, chacune ayant sa propre runtime Go.
- Pour les opérations CPU-intensives, C ou Rust restent nettement plus performants que PL/pgSQL ou Go, limitant les cas d'usage.
