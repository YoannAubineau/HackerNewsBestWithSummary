## Discussion sur Hacker News (62 commentaires)

**Avis positifs** :
- La nouvelle architecture répond à un besoin réel : les gros dépôts privés des clients d'entreprise de GitHub rencontrent effectivement des problèmes de scalabilité actuels, en particulier sur les vérifications de fusion de PR
- C'est une planification solide pour l'avenir qui améliore l'efficacité globale même aux faibles débits, pas seulement aux limites extrêmes, et réduit la capacité de calcul/disque nécessaire
- L'architecture horizontale existante était déjà opérationnelle ; cette évolution se concentre justement sur la scalabilité verticale (intra-repo) qui était le vrai goulot d'étranglement
- La solution offre à GitHub une marge de manœuvre considérable et reconnaît légitimement que les grandes entreprises du secteur (comme Google autrefois) ont besoin de ce type de capacité

**Avis négatifs** :
- Ce changement architectural n'aide pas avec les pannes actuelles de GitHub ; les techniques de scalabilité horizontale sont réutilisées de l'architecture existante
- Supporter des milliers de pushes par seconde par dépôt est symptomatique de mauvaises pratiques (agents générant du code non testé, trop de petits commits inutiles) plutôt qu'un cas d'usage légitime à encourager
- L'ironie de la complexité du contrôle de source distribué combinée à la centralisation des points de défaillance uniques (GitHub comme source de vérité) n'est pas résolue
- GitHub pourrait simplement implémenter des limites de débit et des contrôles d'utilisation plutôt que de construire une infrastructure massive pour supporter des modèles d'utilisation dysfonctionnels liés à l'IA
- La solution semble sur-ingéniérée pour le problème réel : une simple partition par dépôt avec des systèmes standards devrait suffire pour la plupart des besoins de synchronisation
