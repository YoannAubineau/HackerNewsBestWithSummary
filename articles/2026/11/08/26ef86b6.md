## Résumé de l'article

Devvm est un outil open source qui crée une machine virtuelle sandbox dédiée à chaque projet, pré-configurée avec les dépendances et outils détectés automatiquement. Elle offre un environnement isolé pour exécuter du code et des agents IA (Claude Code, Codex, opencode) sans risque pour la machine hôte.

- Détection automatique des chaînes d'outils nécessaires selon les fichiers du projet et création d'une VM en une seule commande, sans configuration complexe
- Isolation de sécurité : les VMs sont sandboxées avec un contrôle réseau par défaut (accès via allowlist), les secrets restent sur la machine hôte tandis que la VM reçoit des placeholders
- Intégration développeur : montage du dossier projet au même chemin, forwarding automatique des ports, support de VS Code via Remote-SSH, compatibilité avec devcontainer.json
- Partage efficace des ressources : première VM crée une image de base, les VMs suivantes se copient en quelques secondes et partagent les outils compilés en lecture seule
- Personnalisation : couches personnalisées (scripts de setup), support de conteneurs Docker en image de base, configuration des agents et outils via --tools et devvm setup, protection du .git sur macOS

## Discussion sur Hacker News (75 commentaires)

**Avis positifs** :
- Répond à un besoin réel : l'isolation des projets pour les agents IA est devenue une préoccupation majeure, et le design de sécurité du projet (isolation du kernel, protection des secrets, isolation réseau et disque) semble bien pensé
- Approche pratique supérieure aux alternatives légères : contrairement à bubblewrap ou systemd seuls, une VM offre une véritable isolation du kernel protégeant contre les exploits noyau, plutôt que juste des namespaces Linux
- Nombreux développeurs travaillent activement sur des problèmes similaires : l'intérêt communautaire pour ce type de solution confirme son utilité, avec plusieurs projets parallèles utilisant libvirt, cloud-init, incus ou krunkit
- Potentiel d'amélioration significatif de la productivité pour développeurs individuels et petites équipes : l'automatisation du setup de VMs par projet réduit la friction comparé à configurer manuellement Vagrant ou multipass
- Intégration de proxy HTTP pour gérer l'accès aux ressources protégées : c'est un pattern émergeant utile pour contrôler l'accès aux registres privés et services sans exposer les credentials au VM

**Avis négatifs** :
- Problèmes d'UX de sécurité : la méthode d'installation via curl script et la demande de login initial génèrent une légitime méfiance ; Docker Sandbox souffre des mêmes problèmes
- Manque de flexibilité architecturale : forcer 1 VM par répertoire est rigide pour les workflows réels où plusieurs repos sont souvent montés dans une même VM, limitant les cas d'usage pratiques
- Beaucoup de projets concurrents déjà matures : smolvm, incus, libvirt+cloud-init, Docker Sandbox, et autres outils existants couvrent déjà les besoins ; ce projet n'offre pas de différenciation claire suffisante
- Inadapté aux environnements d'entreprise complexes : ne gère pas les besoins réels des ingénieurs en grand groupe (accès à des dizaines de repos, isolation de GPU, RDP Retina, injection de credentials sophistiquée, sandboxes longue durée)
- Fondamental non résolu : plus on restreint les agents en termes de permissions, moins ils deviennent utiles ; accorder l'accès nécessaire (dépôts, logs, infra interne) crée rapidement des brèches de sécurité, un dilemme que ce projet ne résout pas mieux que les alternatives
