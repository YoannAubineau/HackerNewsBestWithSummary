## Résumé de l'article

Fast-Anything est un outil qui identifie automatiquement les fonctions critiques ralentissant une application, puis les porte en Rust via un agent d'IA, en validant les résultats sur des appels réels enregistrés avant activation. L'outil fonctionne comme un processus réversible en une seule commande, sans réécriture complète du projet.

- Workflow automatisé : profiling des goulots, portage en Rust par agent (Claude, Codex, etc.), vérification sur cas réels et cas limites (NaN, infinité, entrées déformées), activation optionnelle
- Compilation rapide : chaque port est un micro-crate compilé en secondes, avec cache partagé `.fast/target`
- Zéro risque : portage opt-in par fonction, code original préservé, retour arrière possible via `FAST_ANYTHING_DISABLE=1`
- Support multi-langage : compatible Python, Node.js, Bun, Deno, Ruby, Java, Go, PHP, C/C++, C# ; fonctionne via pont C/JSON sans bindings
- Intégrations : plugin Claude Code, serveur MCP (8 outils), skills d'agent pour apprendre la boucle de portage

## Discussion sur Hacker News (143 commentaires)

**Avis positifs** :
- La stratégie de réécrire seulement les 5% critiques en Rust est pragmatique et évite la complexité d'une réécriture complète, particulièrement quand Python gère bien le reste
- Rust offre des avantages bien au-delà de la performance : sécurité mémoire, correction logique via le système de types fort, et une meilleure vérifiabilité pour les LLMs qui génèrent du code
- Des cas réels montrent des gains significatifs : migrations Python→Rust de 50x à 100x selon les charges de travail CPU-bound, réductions dramatiques de mémoire et latence pour les applications critiques
- Le FFI Rust-Python fonctionne bien pour les hotspots numériques ou traitement de données, comme montré avec PyTorch/NumPy ; les LLMs rendent maintenant ces réécriture ciblées beaucoup plus accessibles
- L'approche hybride évite les pièges des solutions monolingues : une base de code Python maintenable avec des primitives haute-performance en Rust pour les goulets d'étranglement réels

**Avis négatifs** :
- Le problème des goulots d'étranglement diffus : selon la loi d'Amdahl, cette stratégie ne fonctionne que si les 5% critiques dominent réellement. Souvent la performance est répandue 'comme du sable' partout, rendant les optimisations localisées inefficaces
- Le coût caché du FFI et de l'empaquetage : les allers-retours entre Python et Rust pour marshaler les données effacent souvent les gains de performance, sauf pour les cas très spécifiques (calcul intensif, peu de transferts)
- Complexité de maintenance et dette technique : introduire Rust dans une base de code Python crée une 'boîte noire' incomprise par la plupart des développeurs, érodant la maintenabilité et augmentant les bugs potentiels
- Les vrais problèmes sont architecturaux : mauvaises structures de données, décisions de cache inefficaces, ou problèmes I/O/réseau résolus par des améliorations algorithmiques ou refactoring, pas par un changement de langage
- Les LLMs encouragent les réécriture hâtives au lieu d'optimisation réelle : avec l'IA, on risque de passer directement à Rust sans profiler ni comprendre les véritables goulots, en oubliant que replanifier l'architecture en Python aurait pu suffire
