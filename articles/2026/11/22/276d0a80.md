## Résumé de l'article

Zero C# est un fork du compilateur bflat qui compile le code C# directement en petit programme natif sans runtime .NET ni garbage collector. Le langage garde la syntaxe C#, la vérification de types et les génériques, mais la gestion mémoire utilise des arènes libérées en bloc plutôt que d'un garbage collector.

- Le même code source compile pour Linux, macOS, Windows, WebAssembly, DOS sur 386, et firmware UEFI sans système d'exploitation
- Les binaires résultants sont très compacts : 11 KB sur Windows, 40 KB sur Linux, 15 KB en WebAssembly
- C# 15 reste supporté avec unions, extension members, vrais génériques, interfaces, records, lambdas et threads parallèles
- La gestion mémoire s'effectue via des arènes (allocateurs) qu'on libère explicitement, et un chaîne de caractères se formate directement en sortie sans allocations temporaires
- Les exceptions disparaissent (throw arrête le programme) et les erreurs se retournent via des unions ; pas de réflexion ni d'async

## Discussion sur Hacker News (122 commentaires)

**Avis positifs** :
- Arena-based memory management offre un contrôle explicite sur l'allocation/désallocation sans les pénalités de performance de malloc/free, utile pour les domaines critiques en latence (jeux, temps réel)
- C# sans GC peut générer des binaires beaucoup plus petits et avec un temps de démarrage réduit, particulièrement pour des applications spécialisées et des démos
- Le projet démontre qu'il est possible d'avoir la syntaxe ergonomique de C# tout en conservant un contrôle bas niveau comparable à C/C++, offrant une alternative aux langages à bas niveau existants
- Utile pour les contextes très spécifiques comme les compilateurs, les jeux de démoscène, ou les applications embarquées où le GC cause des pauses imprévisibles problématiques

**Avis négatifs** :
- L'écosystème C# complet n'est pas supporté : pas de réflexion, pas de bibliothèque standard complète, nécessitant une réécriture totale du code existant pour chaque projet
- Le GC n'est pas vraiment un problème en 2024 : les GC modernes en C# avec mark-and-sweep générationnel ne causent pratiquement plus de pauses perceptibles, et des outils comme SustainedLowLatency, NativeAOT et Span<T> résolvent déjà les cas critiques
- Les arènes imposent des contraintes fortes sur la gestion de la durée de vie des objets et limitent les algorithmes possibles, notamment en contexte concurrent, sans résoudre fondamentalement les fuites mémoire ou la corruption
- Comparé à Rust ou Zig, ce projet propose un sous-ensemble moins utile : pas de sécurité mémoire statique à la compilation, pas d'écosystème établi, et pire qu'une simple utilisation de C/C++ ou Rust avec une meilleure syntaxe
- Les développeurs C# ne sont pas préparés à la gestion manuelle de la mémoire, rendant ce projet peu attractif pour la communauté C# existante, qui préfère rester sur Rust ou C++ si la gestion manuelle est requise
