## Résumé de l'article

Un script malveillant de vol de numéros de carte bancaire a été découvert sur les sites en ligne de Lascana, Samsonite, American Tourister, Revolve et FWRD avant le Black Friday. Ce script utilise la technologie WebRTC pour extraire les données de paiement (numéro de carte, date d'expiration, code de sécurité) ainsi que les informations personnelles des clients, puis les transmet à des attaquants par un canal de communication contourné par les outils de sécurité courants.

- Le script a été injecté de trois manières différentes : via des paramètres de banneau de consentement, des fichiers CDN partagés ou des pixels de suivi publicitaires, puis chargeait du code supplémentaire depuis des buckets Amazon S3.
- L'attaque cible spécifiquement les appareils mobiles et les pages de paiement, en utilisant WebRTC comme canal caché pour extraire les données, ce qui échappe aux règles de sécurité du Content Security Policy (connect-src) qui surveille les requêtes web ordinaires.
- Les données volées transitent par un relais Cloudflare et communiquent avec l'infrastructure contrôlée par les attaquants via des domaines factices (northbridgeads[.]com), rendant l'attaque difficile à détecter.
- Tous les sites touchés ont supprimé le script malveillant après notification le 24 ou 25 novembre ; le nombre de données de clients potentiellement compromises reste inconnu.
- Les propriétaires de sites doivent immédiatement mettre en place une règle Content Security Policy stricte et auditer les pixels de suivi chargés sur les pages de paiement et connexion.

## Discussion sur Hacker News (208 commentaires)

**Avis positifs** :
- Le blocage des publicités est justifié pour des raisons de sécurité : les réseaux publicitaires sont depuis longtemps infestés de malware et les entreprises refusent de fournir des outils aux éditeurs pour prévenir les escroqueries
- CSP (Content Security Policy) stricte est une mesure de défense essentielle que les sites e-commerce devraient mettre en place immédiatement sur leurs pages de paiement
- Les sites devraient rediriger vers des pages de paiement hébergées par le prestataire plutôt que d'inclure des formulaires de carte directement, réduisant ainsi la surface d'attaque
- Le problème fondamental réside dans l'architecture du web permettant à des tiers de modifier les pages sans contrôle adéquat, et dans la confiance aveugle envers le code tiers exécuté
- Les responsables de site sont plus responsables que les tiers malveillants puisqu'ils ont autorité sur leurs propres pages et devraient être tenus légalement responsables des conséquences de l'intégration de scripts tiers

**Avis négatifs** :
- WebRTC n'est qu'un mécanisme d'exfiltration parmi d'autres : HTTP requests, DNS lookups, ou balises img auraient tout aussi bien fonctionné, le problème n'est pas techniquement spécifique à WebRTC
- Bloquer les ads est une solution cosmétique au problème réel : il faudrait plutôt bloquer tous les scripts tiers non essentiels ou implémenter un véritable sandboxing des iframes
- Il n'y a pas d'alternative viable économiquement pour les sites : les acheteurs d'annonces ne font pas confiance sans JavaScript arbitraire, et imposer des images statiques éliminerait l'accès aux marchés publicitaires
- Le problème ne peut être résolu par la responsabilité juridique seule car les criminels sont souvent injougnables et insolvables, tandis que les véritables solutions nécessitent une refonte architecturale du web
- Cibler les appareils mobiles n'a rien à voir avec les capacités de WebRTC mais simplement avec le fait que les tests automatisés s'exécutent principalement sur desktop et que les outils de développement y sont plus accessibles
