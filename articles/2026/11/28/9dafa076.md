## Résumé de l'article

unkernel est un noyau Linux 7.x compilé en un seul module WebAssembly avec une véritable MMU, capable de démarrer jusqu'à un shell interactif en moins d'une seconde. Le noyau (appels système, ordonnanceur, gestion mémoire, ext4, TCP/IP) s'exécute en code compilé plutôt qu'émulé, tandis que les programmes utilisateurs non modifiés en aarch64 (ARM64) s'exécutent via un émulateur intégré, permettant aux packages Alpine et Debian de fonctionner tels quels dans le navigateur ou Node.js sans serveur.

- Le noyau Linux réel compile directement en WebAssembly avec un vrai MMU (tables de pages Sv48), gérant fork, mmap, copy-on-write, threads et signaux comme sur du matériel réel
- Les appels système atteignent des latences proches du natif (getppid ~170 ns, fork+exit+wait ~60 µs) grâce à l'exécution WebAssembly directe sans hardware virtuel émulé
- Le système inclut les systèmes de fichiers Linux réels (ext4, overlayfs, tmpfs, FUSE, 9p), la pile TCP/IP avec DHCP et DNS, cgroups, namespaces, et périphériques (framebuffer, clavier, souris, son ALSA)
- Un JIT compile le code ARM64 chaud en modules WebAssembly à l'exécution, accélérant le code user de 1,6 à 2,3x comparé à l'interprète seul, notamment pour OpenSSL (AES-128-GCM ~100 MB/s, SHA-256 ~160 MB/s)
- Le SDK TypeScript MIT (sans dépendances fermées) permet d'embarquer Linux dans des applications, avec accès aux disques ext4 locaux, images HTTP, stockage IndexedDB persistant, montages 9p bidirectionnels, vsock, mémoire partagée zero-copy, GL et Vulkan

## Discussion sur Hacker News (80 commentaires)

**Avis positifs** :
- Démontre qu'un vrai noyau Linux compilé en WebAssembly fonctionne et peut exécuter des logiciels inchangés (Postgres, Doom, CLI tools), avec une friction quasi nulle pour déployer des environnements Linux dans le navigateur
- Ouvre des cas d'usage pratiques : sandboxes, environnements éphémères, playgrounds, outils éducatifs, et potentiellement des environnements de développement isolés directement dans le navigateur sans serveur distant
- Représente un exploit technique intéressant et impressionnant pour les développeurs, même si les applications pratiques restent à définir; valide l'approche comme alternative viable aux approches purement émulées
- Facilite la démonstration de logiciels réels en supprimant les friction d'installation et de configuration, rendant l'expérimentation accessible instantanément

**Avis négatifs** :
- Les performances restent limitées : les tests montrent une lenteur significative (40% plus lent que jslinux dans certains cas), principalement à cause du surcoût d'émulation du MMU qui ajoute 2-3x le coût d'accès mémoire
- Les cas d'usage pratiques revendiqués (hébergement d'apps web, dev envs) sont moins attractifs que les solutions établies existantes : limitations mémoire, overhead de montage de fichiers, et fiabilité inférieure aux méthodes industrielles actuelles
- Une approche JavaScript JIT (Korz) peut obtenir des performances 15-50x meilleures que WebAssembly pour certains émulateurs en permettant une compilation plus fine de code répétitif; cela remet en question l'intérêt de WebAssembly pour ce cas d'usage
- Le manque de primitives WebAssembly critiques (setjmp sans tricks Emscripten, préemption forcée des processus) rend l'implémentation userspace complexe et laborieuse
- Soupçons d'utilisation d'IA pour certains aspects du projet, ce qui remet en question la nature réelle de l'accomplissement et alimente le scepticisme sur la valeur réelle versus la valeur affichée
