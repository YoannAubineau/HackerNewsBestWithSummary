## Résumé de l'article

OpenSSL patche une vulnérabilité critique (CVE-2026-121481) de débordement de buffer dans la fonction EVP_EncodeBlock(), utilisée pour l'encodage en base64. La faille permet à un attaquant de causer un dépassement mémoire en fournissant des entrées invalides.

- Le correctif rejette les entrées invalides (buffers NULL, longueurs négatives, longueurs dont la taille encodée dépasserait un entier) en retournant -1
- Une protection similaire est proposée pour EVP_DecodeBlock() et la fonction base64encode() de http_client.c
- La vulnérabilité peut être exploitée via la ligne de commande OpenSSL en passant une valeur `-proxy_pass` très grande à `openssl s_client`
- Des tests sont ajoutés à test/base64_dec_avx2_test.c et la documentation est mise à jour dans EVP_EncodeInit.pod
- Le pattern de cette CVE est similaire à CVE-2021-23840, également un débordement de buffer dans une fonction de codage

## Discussion sur Hacker News (298 commentaires)

**Avis positifs** :
- OpenSSL a longtemps une qualité de code et une conception d'API notablement mauvaises, confirmées par des forks successifs (BoringSSL, LibreSSL) depuis Heartbleed
- Le bug révèle des problèmes structurels : l'API force les appelants à calculer manuellement la taille du buffer sans validation interne, un anti-pattern dangereux
- L'impact réel est limité : seul OpenSSL 4.x (sortie récente) est affecté, les distributions enterprise restent sur les versions 3.x, réduisant considérablement la surface d'exposition
- Le score CVSS 9.8 est exagéré et reflète un problème systémique de scoring : les CVE spectaculaires mais peu exploitables en pratique gonflent les chiffres et créent une fatigue de vulnérabilité

**Avis négatifs** :
- La vulnérabilité est théoriquement sérieuse (débordement de buffer avec potentiel code arbitraire) mais pratiquement difficile à exploiter dans des scénarios réalistes de TLS/HTTPS
- Le rewrite complet en Rust n'est pas une solution miracle : les bibliothèques de crypto Rust actuelles reposent sur des implémentations C/assembly (aws-lc-rs, ring), gardent les mêmes problèmes de sécurité temporelle
- Les alternatives (LibreSSL, BoringSSL, rustls) restent fragmentées et n'ont pas remplacé OpenSSL malgré des décennies ; LibreSSL souffre de manque de portabilité, rustls n'est pas au niveau production pour tous les cas
- Aucune solution unique et standardisée n'émerge ; les grosses organisations financent des forks internes (Google/BoringSSL, AWS/aws-lc) plutôt que de converger sur une pile commune
