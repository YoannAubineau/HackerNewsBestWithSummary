## Résumé de l'article

CVE-2026-98432 est une vulnérabilité use-after-free (lecture de mémoire libérée) dans le noyau Linux affectant la poignée de main TCP IPv4. Elle permet à un attaquant distant et non authentifié d'exécuter du code arbitraire en tant que root, particulièrement sur les serveurs avec des auditeurs TCP multicheminement (MPTCP), sans aucune interaction utilisateur requise. Le noyau Linux fixe cette faille depuis octobre 2026 dans les versions 5.10.272, 5.15.223, 6.1.190, 6.6.159, 6.12.113, 6.18.56, 7.2.10 et 7.3, mais de nombreuses distributions n'ont pas encore publié les correctifs.

- La vulnérabilité affecte tout noyau Linux 4.4 ou ultérieur dépourvu du correctif ; elle s'active avant que l'application n'authentifie la connexion, lors de la poignée de main TCP au niveau du noyau.
- Le bug réside dans le traitement des options IPv4 : le noyau réutilise des données depuis un socket de requête sans les copier, puis les libère immédiatement alors qu'un autre CPU peut encore les lire, causant une condition de concurrence.
- Les programmes Go ouvrent par défaut des auditeurs MPTCP à partir de la version 1.24 ; Anthropic rapporte que Claude a généré un PoC fonctionnel exploitant cette configuration spécifique en 48 minutes pour fuir un pointeur noyau et 5 minutes supplémentaires pour exécuter du code arbitraire.
- Debian, SUSE, Oracle Linux et Amazon Linux disposent de noyaux corrigés ; Ubuntu et Red Hat n'ont pas encore publié de correctifs en production au 31 octobre 2026, bien que Red Hat ait relevé la sévérité en Critical et proposé une atténuation par règles nftables supprimant les paquets TCP avec options IPv4.
- En attendant un correctif, les mitigations incluent : désactiver MPTCP (net.mptcp.enabled=0), appliquer des règles firewall bloquant les paquets TCP avec options IPv4, ou maintenir les auditeurs MPTCP hors d'internet.

## Discussion sur Hacker News (159 commentaires)

**Avis positifs** :
- La vulnérabilité est réelle et critique : elle affecte le code TCP que chaque serveur Linux exécute, avec un CVSS de 9.8 et permet l'exécution de commandes en root sans authentification sur les systèmes multi-cœurs avec MPTCP activé.
- Les programmes Go activent MPTCP par défaut, tout comme Caddy et Tailscale, rendant le problème plus répandu que prévu ; même les distributions Linux modernes (Ubuntu 25+, OpenWRT 25.12+) sont affectées par défaut.
- Le délai de correction par les distributions majeures (Ubuntu, RHEL) est inacceptable pour une vulnérabilité critique : plusieurs semaines après la divulgation responsable, les correctifs ne sont toujours pas disponibles en stable, seulement en « proposed ».
- Cette découverte par les LLM/Claude démontre que les modèles d'IA peuvent trouver des failles graves dans du code C critique ; elle relance le débat sur la nécessité de réécrire des composants critiques dans des langages plus sûrs comme Rust.
- Les atténuations existantes (bloquer les paquets avec options IPv4, désactiver MPTCP) sont insuffisantes ou incomplètes ; seules les mises à jour du kernel offrent une protection réelle.

**Avis négatifs** :
- L'exploitation est complexe et peu probable en pratique : elle nécessite plusieurs CPU, 48 minutes pour exfiltrer un pointeur kernel, puis 5 minutes supplémentaires pour obtenir un shell ; la plupart des routeurs low-cost fonctionnent sur un seul cœur.
- La plupart des appareils (routeurs grand public, IoT) ne sont pas affectés car ils tournent sur des noyaux très anciens (2.x, 3.x) ou sur un seul cœur ; les routeurs sans services TCP ouverts par défaut (OpenWRT) ont un impact minimal.
- Sur les infrastructures cloud bien configurées (AWS avec ALB/NLB, services managés), l'impact est faible car les utilisateurs ne reçoivent pas de connexions TCP directes d'Internet ; Amazon a recommandé un délai de 30 jours pour les instances auto-gérées.
- L'alarmisme sur les LLM trouvant des exploits est exagéré : les bugs de mémoire C préexistaient depuis longtemps et ne sont pas « causés par l'IA » ; trouver la vulnérabilité ne signifie pas que les défenses existantes sont inutiles.
- Beaucoup d'alternatives de mitigation existent et fonctionnent : bloquer les paquets TCP avec options IPv4 en iptables/ufw, désactiver MPTCP via sysctl, ou utiliser IPv6 ; plusieurs utilisateurs confirment que ces règles ne causent aucun problème opérationnel.
