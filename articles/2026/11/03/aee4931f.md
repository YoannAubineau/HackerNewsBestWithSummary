## Résumé de l'article

Un site web et une API permettent de consulter les tables d'appels système (syscalls) Linux pour chaque architecture processeur, avec l'historique complet des versions du noyau où chaque syscall a été ajouté ou supprimé. Les données sont extraites directement du code source du noyau Linux et incluent les conventions d'appel, les numéros de syscall et les arguments pour chaque plateforme.

- Les tables pour chaque architecture (x64, x86, ARM, etc.) sont disponibles en JSON via une API REST (api.syscall.sh/v2) et téléchargeables directement du site
- Le site permet de sélectionner différentes versions du noyau Linux et affiche pour chaque syscall sa date d'apparition (since) et sa suppression éventuelle (removed_in)
- Les appels système supprimés restent visibles avec un marquage du noyau qui les a retirés
- Les descriptions courtes proviennent du projet Linux man pages et de liburing ; l'API documente aussi les conventions d'appel (numéro en NR, arguments en ARG0-ARG5, résultat en RETURN)
- Le générateur scanne les sources du noyau (tables SYSCALL_DEFINE et tables d'expédition) pour chaque version majeure, garantissant l'exactitude des données dispatché

## Discussion sur Hacker News (51 commentaires)

**Avis positifs** :
- Le site offre une ressource officielle et à jour directement générée depuis les sources du noyau Linux, bien plus fiable que des sources tierces obsolètes
- L'approche de documenter chaque numéro de syscall distinct comme entrée ABI est factuelle et objective, indépendamment des similarités fonctionnelles entre appels
- L'automatisation du pipeline de mise à jour (script générant JSON depuis les sources, rechargement hebdomadaire via API) rend le site maintenable et extensible à long terme
- Le projet remplit un besoin éducatif réel pour ceux qui apprennent l'assembleur et l'ABI système sur différentes architectures

**Avis négatifs** :
- Le site manque de signalement clair des syscalls obsolètes ou dépréciés (ex: pipe vs pipe2, open vs openat), ce qui pourrait induire les utilisateurs à adopter des interfaces suboptimales
- La distinction entre 400+ syscalls devient largement cosmétique puisque beaucoup ne sont que des variantes mineures partageant du code implémentation et qu'io_uring consolide progressivement les I/O syscalls
- Le nombre de syscalls varie arbitrairement selon l'architecture sans raison technique forte, résultant d'une numérotation historique indépendante dans les années 90 plutôt que d'une conception unifiée
- Le website peut présenter des problèmes graphiques selon les configurations et certaines informations techniques (ex: utilisation de eax vs rax) ont eu besoin de correctifs
