## Résumé de l'article

Trynix.dev est une plateforme web qui permet d'exécuter n'importe lequel des 300 000 paquets Nix directement depuis un navigateur, en combinant Linux compilé en WebAssembly (unkernel) avec l'émulation de programmes utilisateur. Cette réalisation démontre comment JavaScript et WebAssembly deviennent les langages dominants pour tous les logiciels, confirmant une prédiction de 2035 arrivée plusieurs années plus tôt.

- Trynix exploite unkernel, une version de Linux compilée en WebAssembly qui offre 2 à 32 fois plus de rapidité qu'une approche QEMU entièrement émulée
- La plateforme supporte les interfaces graphiques (Wayland composé en WebGL2), l'audio (ALSA via le navigateur), le réseau (curl, git, pip via WebSocket) et peut exécuter des applications complexes comme Firefox
- L'auteur a démontré un cas limite extrême : Firefox tournant sous Linux en WebAssembly, chargé dans Firefox, capable de charger à nouveau Firefox en cascade
- Ce projet illustre concrètement la thèse de la conférence « The Birth & Death of JavaScript » de Gary Bernhardt sur la domination inévitable de JavaScript/WebAssembly dans tous les domaines logiciels

## Discussion sur Hacker News (111 commentaires)

**Avis positifs** :
- La capacité à exécuter des systèmes d'exploitation complets dans un navigateur (Linux, Windows) est techniquement impressionnante et représente une avancée notable dans la virtualisation web
- WebAssembly offre des performances quasi-natives et une meilleure sécurité que les approches antérieures (asm.js), permettant de porter des programmes existants avec succès
- Des applications pratiques émergent : environnements de développement éphémères, démonstration de logiciels aux utilisateurs sans installation, outils pédagogiques pour l'accès à Linux
- Les investissements massifs dans les moteurs JavaScript/WebAssembly ont créé une infrastructure performante qui bénéficie maintenant à des cas d'usage au-delà du web

**Avis négatifs** :
- WebAssembly n'est pas réellement du JavaScript malgré le titre provocateur : c'est du bytecode distinct avec un runtime différent, donc le parallèle avec la prédiction originale est discutable
- Les performances restent limitées : un rendu nested prend plus d'une heure, et l'exécution émulée via QEMU/WASM demeure beaucoup plus lente que le code natif
- Les cas d'usage pratiques restent niche et incertains : même les promoteurs admettent que les applications réelles de cette technologie n'ont pas encore émergé de façon convaincante
- Les vulnérabilités des langages compilés (C/C++) utilisés pour les noyaux et moteurs subsistent dans WASM ; la sécurité du navigateur elle-même ne résout pas les problèmes fondamentaux
- Le compilage et le téléchargement des dépendances rend l'accès lourd et lent en pratique ; les applications natives Rust/Crystal représentent probablement une meilleure approche pour le futur des applications desktop
