## Résumé de l'article

Vérifier qu'un théorème est correct parce qu'il a été formalisé en Lean (un assistant de preuve informatique) nécessite bien plus que de compiler le code. Bien que Lean offre une garantie mathématique forte, les théorèmes générés par l'IA requièrent quatre vérifications critiques avant de pouvoir affirmer leur validité.

- **L'énoncé Lean doit correspondre à l'énoncé informel** : la formalisation en code doit exprimer exactement le théorème revendiqué dans l'article, pas une version affaiblie ou déformée (risque particulièrement élevé quand des milliers de lignes de code sont importées).
- **Le code doit compiler sans erreur** : c'est une première barrière, mais insuffisante; les bases de code massives peuvent nécessiter des machines puissantes pour la compilation.
- **Le code doit prouver précisément le théorème énoncé, sans tours de passe-passe** : l'outil « lake comparator » vérifie que les définitions intermédiaires n'ont pas été modifiées et que seuls les axiomes mathématiques sont utilisés.
- **Les éventuels bugs du noyau de Lean doivent être exclus** : « lake comparator --paranoid » teste la preuve avec plusieurs implémentations indépendantes du noyau Lean pour éliminer tout risque d'exploitation de défaut.
- **Un code Lean correct ne garantit pas que l'article PDF correspondant soit correct** : il existe des cas où la preuve informatique et la preuve en langage naturel divergent, rendant nécessaire une traduction inversée du Lean vers l'anglais pour vérifier le raisonnement écrit.

## Discussion sur Hacker News (128 commentaires)

**Avis positifs** :
- Les preuves vérifiées en Lean offrent une garantie très forte comparée au simple code compilé, car le système de types encode des propriétés mathématiques qui sont prouvées par le compilateur lui-même.
- Lean dispose d'outils intégrés (comme `lake comparator`) pour détecter les contournements et assurer que seules les axiomes mathématiques sont utilisés, réduisant significativement les risques de triche ou d'exploitation de bugs.
- Avoir une preuve formelle, même imparfaite ou longue, représente un progrès énorme par rapport à l'absence de preuve et permet de détecter les erreurs dans l'énoncé du théorème lors de l'examen du chemin de preuve.
- Pour les mathématiques pures, il est généralement facile pour un expert en Lean de vérifier que l'énoncé formalisé correspond à l'intention mathématique, ce qui isole le problème critique à valider manuellement.
- Les kernels de Lean alternatifs et indépendants (comme Con Leche) réduisent la probabilité qu'un programme puisse exploiter simultanément un bug dans Lean ET dans le vérificateur alternatif.

**Avis négatifs** :
- Les LLMs génèrent des preuves Lean excessivement longues et boursouflées (centaines à milliers de lignes) où il est impossible de comprendre ce qui se passe, contrairement aux preuves humaines qui sont généralement plus concises.
- Sur les 290 théorèmes OpenAI formalisés en Lean, environ 38 ne prouvent même pas le théorème principal de l'article, montrant que les LLMs peinent à encoder correctement l'intention mathématique malgré une compilation réussie.
- Vérifier qu'un énoncé Lean correspond au théorème informel énoncé reste un défi humain majeur, particulièrement quand cet énoncé repose sur des milliers de lignes de définitions importées non vérifiées (10 000+ lignes pour Hodge, 250 000+ pour la classification des groupes simples).
- L'énorme taille des preuves (une preuve de FLT nécessite 500 GB de RAM et 96 cœurs pour vérifier) soulève la question de l'utilité d'une preuve si complexe qu'aucun humain ne peut la comprendre, remettant en cause l'objectif fondamental des preuves mathématiques.
- Même avec un kernel Lean formellement vérifié écrit en Lean, on retombe dans un problème circulaire : c'est du code Lean vérifiant du code Lean, sans vérification externe complètement indépendante.
