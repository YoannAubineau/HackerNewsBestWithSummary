## Résumé de l'article

Cet article répond à la critique selon laquelle les outils d'IA feraient perdre aux ingénieurs leur rigueur et leur engagement envers les systèmes. L'auteur, qui utilise quotidiennement les LLM sur des systèmes critiques, argumente que ces outils amplifient les qualités existantes : les ingénieurs qui se soucient vraiment de la qualité s'en servent pour enfin écrire les tests formels, spécifications TLA+ et analyses exhaustives qu'ils n'avaient jamais le temps de faire, tandis que les négligents continueront simplement à négliger, seulement plus lentement.

- Les récentes pannes (Microsoft 365, United, Apple) reflètent quarante ans de dette technique et de gestion insuffisante, non une défaillance intrinsèque des outils IA
- Le vrai problème réside dans le choix managérial de remplacer les ingénieurs seniors par des abonnements IA bon marché, une stratégie bien antérieure aux LLM et fondamentalement inchangée
- L'IA rend la rigueur coûteuse autrefois réservée aux systèmes critiques (avionique, Bell Labs) accessible sur un projet ordinaire, contredisant l'idée qu'elle dégrade l'engagement
- Le risque réel : les ingénieurs qui contournent les outils sans vérification ni compréhension mentale, mais ce comportement existait avant ChatGPT et refléterait une culture d'entreprise défaillante
- Ce qui distingue les ingénieurs qui donnent vraiment suite c'est leur réaction quand le code casse en production, pas l'outil qu'ils ont utilisé pour le produire

## Discussion sur Hacker News (244 commentaires)

**Avis positifs** :
- Les outils IA amplifieront les personnes consciencieuses qui les utilisent correctement pour résoudre des problèmes complexes, tandis que les mauvais développeurs produiront simplement plus de mauvais code—la qualité du résultat dépend de celui qui les manie.
- Les IA accélèrent le travail de fond (architecture, spécifications, documentation) en permettant aux ingénieurs compétents de concentrer leur énergie sur la validation, la révision et les décisions critiques plutôt que sur la dactylographie répétitive.
- Historiquement, chaque nouvelle abstraction technologique (compilateurs, langages de haut niveau) a d'abord déconcerté les experts avant d'être intégrée ; les LLM suivent le même schéma et demandent une discipline similaire pour être utilisés efficacement.
- Sans outils d'assistance, les délais irréalistes et la pression de la productivité forçaient déjà les ingénieurs à faire des compromis de qualité ; les LLM permettent aux persévérants de maintenir les standards tout en respectant les contraintes.
- Le vrai problème n'est pas l'outil lui-même mais le manque de gouvernance organisationnelle, de code review rigoureux et de responsabilisation—des problèmes qui existaient bien avant les LLM.

**Avis négatifs** :
- Les LLM ne sont pas des abstractions déterministes comme un compilateur ; ils produisent des résultats non-déterministes et impossibles à prédire fiablement, ce qui les rend intrinsèquement incompatibles avec les pratiques d'ingénierie rigoureuse.
- Le coût relatif de 'bien faire les choses' a augmenté : avant, produire de mauvais code était lent ; maintenant les médiocrités génèrent du mauvais code 10x plus vite, surpassant les consciencieux malgré leur accélération parallèle.
- L'atrophie des compétences est inévitable : la compréhension profonde s'acquiert en écrivant du code soi-même ; déléguer aux LLM sans effort cognitif intentionnel érode progressivement l'expertise et le jugement technique.
- Le contexte organisationnel récompense la vélocité brute et pénalise la qualité : les managers voient seulement la rapidité d'exécution et licencient ceux qui prennent 'trop de temps' pour vérifier, peu importe la solidité du résultat.
- L'article lui-même est généré par IA, ce qui sape sa crédibilité—il démontre précisément le problème qu'il prétend résoudre en utilisant un outil sans intention authentique derrière lui.
