## Résumé de l'article

GitHub a connu un incident affectant plusieurs services critiques incluant les pull requests, les opérations Git, les issues, les requêtes API et les Actions. L'incident a été résolu et les dégradations de performance et les défaillances intermittentes ont été atténuées.

- L'incident a provoqué des erreurs élevées et des défaillances intermittentes affectant principalement les pull requests, les opérations Git et les issues
- Une dégradation des performances a également été observée sur les requêtes API et les Actions GitHub
- Les services ont progressivement été stabilisés et l'incident a été déclaré résolu
- Une analyse détaillée des causes racines sera partagée ultérieurement

## Discussion sur Hacker News (132 commentaires)

**Avis positifs** :
- Les alternatives auto-hébergées (Forgejo, Gitea, GitSocial) offrent une fiabilité et une indépendance appréciables pour les déploiements critiques, plusieurs utilisateurs les recommandant après migration réussie
- Des solutions tierces comme Buildkite, Woodpecker CI, ou rwx.com offrent des performances supérieures (2-10x plus rapides) et une meilleure résilience que GitHub Actions
- L'architecture modulaire (scripts de déploiement indépendants + hôte d'intermédiaire) permet de continuer à déployer même en cas de panne GitHub, testée avec succès chez de nombreuses entreprises
- Le workaround HTTPS (git config url) offre une solution temporaire quand SSH échoue, et certains incidents sont liés à des migrations SSH prévisibles plutôt qu'à des défaillances aléatoires

**Avis négatifs** :
- GitHub reste la meilleure solution en classe malgré les problèmes récurrents ; même les utilisateurs conscients des alternatives hésitent à migrer en raison de la complexité
- Les incidents sont trop fréquents (plusieurs par semaine selon certains) et affectent des opérations git essentielles (push/pull), pas seulement la UI, rendant les 99,6% d'uptime revendiqués suspects
- La charge liée aux déploiements basés sur l'IA engorge l'infrastructure sans bénéficier les utilisateurs payants ; GitHub limite les usages gratuits mais ne sacrifie pas les services premium pour maintenir la stabilité
- La page de statut GitHub est peu fiable (reste verte pendant les pannes réelles) et retarde les diagnostics, aggravant le temps d'arrêt pour les équipes utilisant GitOps
- Migrer est coûteux et complexe : self-hosting demande du personnel qualifié, les solutions payantes (Buildkite) coûtent 4x plus cher, et même avec alternatives les dépendances GitHub restent critiques
