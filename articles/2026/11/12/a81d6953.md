## Résumé de l'article

GitHub Actions supporte désormais les fichiers de verrouillage (lockfiles) pour améliorer la sécurité des workflows en évitant les attaques de chaîne logistique. Au lieu de pointer vers des SHA complets ou des tags mutables, cette approche permet de verrouiller les versions des actions tout en maintenant une traçabilité complète.

- Installer l'extension `gh-actions-lock` via `gh extension install github/gh-actions-lock` et exécuter `gh actions-lock` pour générer un fichier `.github/workflows/actions.lock` contenant les références verrouillées de toutes les actions utilisées
- Le lockfile enregistre à la fois les tags sémantiques (v7.0.1) et les SHA complets des commits, permettant à la fois une lisibilité et une vérification cryptographique
- Renovate et Dependabot supportent déjà les lockfiles et mettront à jour automatiquement le fichier lors des mises à jour de dépendances
- Ajouter une tâche CI de vérification (`gh actions-lock --verify`) pour s'assurer que le lockfile reste synchronisé avec les workflows et que les pins verrouillés sont toujours valides en amont
- Utiliser zizmor v1.32.0 ou ultérieur en tant que linter de sécurité pour GitHub Actions, qui reconnaît désormais les lockfiles comme approche conforme

## Discussion sur Hacker News (62 commentaires)

**Avis positifs** :
- Les lockfiles GitHub Actions résolvent le problème critique du chaînage des dépendances transítives, contrairement au simple pinning SHA qui laisse les dépendances indirectes vulnérables.
- C'est une amélioration bienvenue et attendue depuis longtemps, alignant GitHub Actions avec les pratiques de sécurité des autres écosystèmes de paquets (npm, Cargo).
- Le feature enfin permet une approche de sécurité combinée : délai de consommation + vérification de sécurité automatisée, réduisant partiellement les risques de chaîne d'approvisionnement.
- Les lockfiles offrent une meilleure lisibilité et maintenabilité qu'un SHA brut avec un commentaire, tout en gardant la possibilité d'utiliser des SHA si désiré.

**Avis négatifs** :
- La feature ne couvre pas tous les cas : les workflows réutilisables, les images Docker et les commandes internes (npm pull, etc.) restent non lockées ou nécessitent un pinning manuel supplémentaire.
- C'est en réalité un SHA pinning avec étapes supplémentaires et complexité accrue (lockfile séparé à vérifier) sans résoudre le problème fondamental de confiance envers les tiers.
- L'article original ne met pas en avant le chaînage transítif (le vrai bénéfice), créant de la confusion ; certains commentateurs doutent que cela offre une vraie amélioration par rapport aux approches précédentes.
- La meilleure sécurité reste de ne pas utiliser d'actions tierces du tout, ou de les copier dans son propre repo pour avoir un contrôle total plutôt que de compter sur des lockfiles.
- GitHub devrait rendre les tags du marketplace immuables d'office au lieu de laisser les utilisateurs gérer des lockfiles, comme le font d'autres registres de paquets.
