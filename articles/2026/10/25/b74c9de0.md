## Discussion sur Hacker News (95 commentaires)

**Avis positifs** :
- La vulnérabilité est réelle et sérieuse : un débordement de tampon dans brotli peut effectivement mener à une exécution de code à distance, particulièrement pour les clients HTTP (Node.js, Python) qui décodent automatiquement les réponses compressées
- Le correctif existe depuis février 2026 mais Google n'a pas publié de release jusqu'à présent, laissant les dépendants vulnérables pendant des mois malgré les 100+ commits en attente
- L'impact est significatif : des millions de serveurs Python téléchargent brotli via des dépendances indirectes (aiohttp, urllib3, requests, httpx) sans nécessairement en avoir conscience
- Le problème révèle une fragilité systémique : les erreurs C restent dangereuses et les implémentations tierces de brotli peuvent hériter des vulnérabilités en l'absence d'implémentations sécurisées en Rust

**Avis négatifs** :
- La gravité est probablement exagérée : sur les serveurs, la vulnérabilité nécessite des conditions spécifiques (décodage brotli activé par défaut) qui ne sont généralement pas le cas ; c'est essentiellement un problème côté client HTTP
- Aucun exploit complet n'a été publiquement démontré fonctionnant sur des configurations standards, malgré les affirmations du nom 'http2shell' ; les PoC existants ne fonctionnent qu'avec des configurations affaiblies
- La médiatisation sensationnelle et l'attribution à OpenAI/Aikido semblent motivées par des intérêts commerciaux plutôt que par une réelle nécessité de panser, reflétant une tendance problématique à dramatiser chaque CVE
- Le risque réel reste limité car très peu d'applications acceptent du brotli depuis le client côté serveur, et les clients n'accepteront ce contenu que s'ils se connectent à des serveurs malveillants
