## Résumé de l'article

Go 1.27 introduit une amélioration automatique de la réutilisation des connexions HTTP/1 dans net/http.Transport. Auparavant, quand une réponse HTTP/1 n'était pas entièrement lue avant sa fermeture, la connexion était abandonnée et une nouvelle était créée pour la requête suivante, dégradant les performances de façon silencieuse. Désormais, le transport vide automatiquement les corps de réponse non lus en arrière-plan (jusqu'à 50 ms ou 256 KB) pour permettre la réutilisation de la connexion.

- Dans le benchmark présenté, une boucle de 100 requêtes s'exécute 5 fois plus vite en Go 1.27 (~150 ms) qu'en Go 1.26 (~710 ms) grâce à cette optimisation
- HTTP/1 envoie les réponses séquentiellement sur la même connexion ; ne pas lire complètement un corps empêche le transport de trouver le début de la réponse suivante
- Les cas d'usage courants comme lire uniquement le code de statut ou décoder un objet JSON incomplet laissaient des données non lues, cassant la réutilisation
- Go 1.27 gère automatiquement ce problème en vidant de manière asynchrone les corps résiduels, éliminant le besoin de code de contournement complexe
- Les développeurs peuvent désormais fermer les corps de réponse simplement sans craindre une dégradation de performance

## Discussion sur Hacker News (47 commentaires)

**Avis positifs** :
- Permet enfin de supprimer des fonctions utilitaires copiées d'un projet à l'autre pour gérer correctement le drainage des connexions HTTP
- Le compromis de limiter le drainage à 50ms est bénéfique : évite de surcharger la connexion si le réseau est lent tout en permettant la réutilisation
- Amélioration significative de performance mesurée (710ms réduit à 150ms en Go 1.27), particulièrement pertinente pour les microservices utilisant HTTP/1 non chiffré
- Le stdlib Go 'batteries included' avec un support HTTP fort et une documentation claire a été clé au succès du langage, cette amélioration renforce cet avantage

**Avis négatifs** :
- Le comportement implicite de Close() qui draine maintenant les corps n'est pas bien documenté dans net/http lui-même, malgré que ce soit une FAQ fréquente pour les développeurs
- Incompatibilité potentielle avec certains reverse proxies (nginx) et navigateurs qui génèrent des erreurs d'IO ou des codes XHR à 0 quand le corps n'est pas consommé
- HTTP/2 rend cette optimisation inutile mais reste significativement plus lent en Go (issue #47840) ; HTTP/2 nécessite SSL et plusieurs serveurs/proxies ne le supportent pas encore (Cloudfront, nginx basique)
- Cas limites subtils subsistent : json.Decoder laisse traîner des newlines aux limites de puissances de 2 bytes, les réponses chunked ne bénéficient pas du drainage automatique, créant des pièges d'intégration
- L'évolution du code (drainAndCloseBody → drainAndCloseBodyWithTimer → drainAsyncAndCloseBodyWithTimer) montre une complexité croissante pour un problème censément simple, illustrant les difficultés de maintenir des abstractions HTTP
