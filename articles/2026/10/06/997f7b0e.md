## Résumé de l'article

Polars 2.0, une bibliothèque de traitement de données, sortie aujourd'hui, intègre le moteur streaming par défaut, l'out-of-core (spill-to-disk) et le SQL comme citoyen de première classe, avec des gains de performance majeurs et un nouveau type Map.

- Le streaming engine est maintenant le mode par défaut pour collect(), améliorant la mémoire et les performances sur la plupart des requêtes, au prix d'une non-garantie d'ordre des lignes pour certaines opérations (joins, group_by, unpivot) sauf si maintain_order=True est activé
- Le support out-of-core (spill-to-disk) est activé par défaut, commençant à écrire sur disque à ~80% de RAM, avec un budget disque de 64 GB par défaut ; joins et group_by supporteront cette fonctionnalité à l'avenir
- Polars 2.0 surpasse DuckDB 1.5.6, DuckDB 2.0 alpha et DataFusion 54.0.0 sur les benchmarks TPC-H et TPC-DS, avec des améliorations de l'optimiseur et du moteur incluant join reordering et dynamic predicates/bloom filters
- Un nouveau type Map dtype est introduit pour représenter directement les dictionnaires Arrow, avec des méthodes dédiées comme get(), contains_key(), keys() et values()
- Polars adopte une approche plus stricte : les erreurs remontent immédiatement avant compilation du plan de requête plutôt que pendant exécution, favorisant une itération rapide avec les agents d'IA

## Discussion sur Hacker News (85 commentaires)

**Avis positifs** :
- Polars 2.0 offre des améliorations majeures de performance et supporte désormais SQL natif, le positionnant comme concurrent sérieux face à DuckDB et DataFusion sur les benchmarks TPC-H et TPC-DS
- Migration depuis Pandas justifiée : API plus propre et intuitive, vitesse supérieure (52x plus rapide sur le 1 Billion Row Challenge), meilleure scalabilité sans solutions externes, et fondation Rust robuste
- L'écosystème en-mémoire columnar s'améliore avec support des moteurs de streaming, out-of-core capabilities et meilleure gestion de la mémoire, répondant aux limitations historiques
- Adoption croissante dans l'industrie (quant trading, géospatial via GeoPars en développement, analyse météorologique) et amélioration de l'interopérabilité via Narwhals pour les cas génériques
- Competition saine avec DuckDB/DataFusion bénéficie à l'ensemble de l'écosystème et pousse l'innovation dans le traitement de données locales

**Avis négatifs** :
- Les benchmarks maison manquent de transparence : résultats choisis favorisant Polars (réglages thread 32 vs 192, optimisations ciblées), confirmant que chaque projet 'gagne' ses propres benchmarks
- Problèmes de scalabilité sur machines haute-concurrence : sur AWS 192-core avec petites données, Polars limité à 32 threads surpasse le mode par défaut, révélant une surcharge constante élevée
- Limitations fonctionnelles subsistent : pas de support SQL pour asof_join(), gestion des horodatages nanoseconde imparfaite, API string concatenation moins élégante que Pandas malgré les progrès
- DuckDB reste supérieur pour certains cas : consommation mémoire 19x inférieure sur les benchmarks, meilleur choix pour transformations SQL complexes remplaçant 40+ lignes de code
- Adoption encore freinée par effet de réseau Pandas (majorité utilise Pandas pour son ubiquité plutôt que ses mérites), bien que la tendance s'inverse chez les développeurs avertis
