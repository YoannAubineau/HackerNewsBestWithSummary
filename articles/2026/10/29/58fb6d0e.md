## Résumé de l'article

TianoCore EDK II est un projet open source de référence pour la création de firmware UEFI, utilisé par presque tous les fournisseurs de UEFI mondiaux (AMI, Insyde, Phoenix, Microsoft) pour les serveurs et centres de données. Une faille critique de corruption mémoire (CVE-2026-97631, sévérité 9.5/10) a été découverte dans un composant ICMP, permettant l'exécution de code avant le démarrage du système d'exploitation et avant l'activation de protections comme Secure Boot et le TPM.

- La vulnérabilité a été découverte par des chercheurs d'Anthropic et de Google, programmée pour divulgation coordonnée en janvier, mais exposée publiquement par une pull request d'AMI le mois dernier
- Les attaquants pourraient installer des payloads malveillants au niveau du firmware qui s'exécutent à chaque démarrage, même sans persistance du premier payload
- La disponibilité publique du code de correction rend trivial pour les pirates avancés de comprendre le mécanisme et de développer des exploits
- La correction de cette vulnérabilité sur des millions d'appareils gérés par des milliers de fournisseurs est un processus lent et complexe

## Discussion sur Hacker News (242 commentaires)

**Avis positifs** :
- La vulnérabilité contourne les mécanismes de sécurité critiques : elle permet de contourner Secure Boot et le measured boot, ce qui peut désactiver BitLocker et compromettre les clés TPM utilisées pour le chiffrement de disque
- Les implications pour les environnements d'entreprise sont sérieuses : elle affecte les serveurs bare-metal des hébergeurs, les laptops d'entreprise configurés pour le netboot, et les thin clients, représentant une surface d'attaque réelle même si limitée
- L'accent sur la minimisation du code est justifié : un million de lignes de code UEFI crée une surface d'attaque énorme que même les LLMs peuvent exploiter systématiquement, tandis que du firmware hyperspécifique de 300 lignes éviterait ces classes entières de vulnérabilités
- Le problème révèle une architecture défectueuse : UEFI a concentré trop de fonctionnalités (réseau, affichage, USB) dans le firmware critique, quand ces services devraient être optionnels ou implémentés au niveau de l'OS

**Avis négatifs** :
- La surface d'attaque pratique est extrêmement réduite : l'attaquant doit être sur le même réseau local, avoir les machines en boot PXE, synchroniser l'exploit avec un redémarrage, et PXE boot n'est pas actif par défaut sur la plupart des machines personnelles
- Le problème peut être facilement évité : les organisations bien configurées isolent les réseaux de gestion, les administrateurs peuvent désactiver PXE dans le BIOS, et les pare-feu peuvent filtrer les paquets ICMP malformés
- C'est du « crying wolf » excessif : si un attaquant a accès au réseau pour envoyer des paquets ICMP ciblés, il peut déjà servir des images de boot malveillantes via PXE sans avoir besoin d'exploits complexes
- Les solutions « small code » ne sont pas panacée : réécrire tout en code minimal coûte énormément et les dépendances externes créent leurs propres vulnérabilités ; seL4 et les microkernels restent théoriques pour les systems réels
- La notation CVSS de 9,5 est gonflée : comparée au PHP RCE (9,2) qui lui était plus critique, cette vulnérabilité nécessite des conditions très spécifiques et n'affecte qu'une fraction des serveurs mondiaux
