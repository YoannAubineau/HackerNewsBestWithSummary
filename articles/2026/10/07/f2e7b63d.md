## Résumé de l'article

Chrome 155 introduit le décodage natif du format JPEG XL (.jxl), un format d'image nouvelle génération offrant 30-50 % de meilleure compression que JPEG, la compression sans perte, le support HDR intégré et le transcodage JPEG sans perte. Le décodeur a été réimplémenté en Rust pour garantir la sécurité mémoire et éliminer les vulnérabilités historiquement présentes dans les décodeurs en C++.

- Le format JPEG XL offre des avantages significatifs : compression 30-50 % meilleure que JPEG, support natif du HDR, compression sans perte et transcodage JPEG sans perte, idéal pour les images photographiques haute fidélité
- Le décodeur a été écrit en Rust (jxl-rs) pour éliminer les risques de sécurité mémoire (débordements, accès hors limites, use-after-free) présents dans les décodeurs C++ traditionnels
- Les optimisations de performance utilisent une couche d'abstraction SIMD (jxl_simd) inspirée de la bibliothèque C++ Highway, permettant des instructions SIMD sans code non sécurisé
- Le décodeur Rust a été validé par fuzzing et examen de code assisté par IA, sans aucun bug de sécurité mémoire détecté
- Cette décision répond aux demandes cohérentes des développeurs web, visibles notamment dans le projet Interop 2026

## Discussion sur Hacker News (264 commentaires)

**Avis positifs** :
- JPEG XL offre des avantages techniques substantiels : meilleure compression que JPEG/PNG, support du lossless et lossy, transparence, HDR natif, et capacité à transcoder les JPEG existants sans perte, ce qui en ferait un format universel remplaçant plusieurs formats actuels
- Le support navigateur s'étend rapidement : Chrome et Firefox le supportent, Safari sur macOS/iOS également, et le format gagne en adoption sur les OS majeurs, contrairement à WebP qui a pris des années
- La réécriture en Rust de Google (jxl-rs) a résolu les problèmes de sécurité de la bibliothèque C++ originale, satisfaisant les exigences de sécurité des navigateurs tout en maintenant les performances
- L'adoption par Adobe et le PDF 2.0 forcent les platforms à supporter le format, créant un effet de réseau positif ; les applications natives sur macOS/iOS gagnent déjà le support automatiquement
- Contrairement à WebP, JPEG XL bénéficie d'un large soutien de l'industrie (Apple, Netflix, Microsoft, etc.) et d'une licence royalty-free, éliminant les craintes de brevets qui ont entravé d'autres formats

**Avis négatifs** :
- Le format souffre d'une fragmentation d'adoption : beaucoup de logiciels (éditeurs d'images, applications mobiles, systèmes d'exploitation anciens) ne le supportent pas encore, créant les mêmes frustrations que WebP (fichiers téléchargés inutilisables hors navigateur)
- La complexité du format (100 000 lignes de code en C++) et les exigences de calcul élevées pour l'encodage côté serveur rendent le déploiement coûteux, notamment pour les uploads utilisateurs ou le transcodage dynamique
- Il existe un scepticisme sur la nécessité réelle du format : les connexions modernes et les formats existants suffisent pour la plupart des cas d'usage web, et l'ajout d'un énième format fragmente l'écosystème plutôt que de l'unifier
- AVIF reste compétitif ou supérieur pour la compression lossy très agressive (images thumbnail, compression extrême), et certains tests suggèrent qu'AVIF peut surpasser JPEG XL dans ces scénarios courants sur le web
- La décision de Google de retirer puis réintégrer le support sème la méfiance : le revirement soudain suggère des calculs politiques/corporatifs plutôt qu'une conviction technique, risquant l'abandon futur du format
