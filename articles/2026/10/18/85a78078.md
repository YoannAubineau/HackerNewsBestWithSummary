## Résumé de l'article

Sphinx est un hook Git open source et gratuit conçu pour le développement assisté par agent IA. Avant de valider le code généré, il pose au développeur des questions sur le fonctionnement réel de ce code, notamment dans les scénarios d'erreur, pour garantir que le développeur comprend ce qu'il va livrer.

- Le tool fonctionne en trois étapes : l'agent ou le développeur pousse du code, Sphinx pose une question sur le diff sans accès aux discussions antérieures, le développeur répond et apprend en cas d'erreur ou continue si correct
- Compatible avec les principaux outils d'IA coding (Claude Code, Cursor, Codex, etc.) et optimisé pour fonctionner avec peu de tokens via un agent existant, OpenRouter ou tout endpoint compatible OpenAI
- Protège la sécurité : les réponses ne remontent jamais à l'agent IA et les fichiers .env ou clés d'accès ne sont jamais inspectés
- Installation simple en une minute avec npm ; offre un mode « sphinx yolo » pour contourner les vérifications en urgence avec journalisation des suppressions

## Discussion sur Hacker News (75 commentaires)

**Avis positifs** :
- Utile pour les équipes qui pushent du code IA sans véritable compréhension, et pour ralentir les pratiques negligentes tout en encourageant l'intentionnalité
- Peut aider les mainteneurs OSS et les reviewers à structurer leurs audits de PR, particulièrement sur de gros changements
- Complément légitime aux pratiques de code review existantes, notamment pour identifier les hypothèses sous-jacentes aux changements et tester leur validité
- Utile comme outil de sensibilisation : avec le doublement du nombre de devs tous les 3 ans, ce type de garde-fou peut jouer le rôle d'avertissement similaire aux anciens conseils contre le copier-coller StackOverflow

**Avis négatifs** :
- Inefficace sur les deux extrêmes : inutile pour ceux qui comprennent déjà leur code, et rejeté par ceux qui ne s'en soucient pas ou qui utiliseront un agent IA pour contourner le hook
- Ne détecte que la compréhension du quoi, pas la qualité architecturale ni les erreurs subtiles (debug prints oubliés, imports cassés, edge cases) qui vivent dans les diffs
- La vraie solution est une culture du code review humain rigoureux et une meilleure compréhension initiale ; c'est un pansement sur une hémorragie d'incompétence systémique
- Risque de devenir une case à cocher supplémentaire dans un processus déjà surchargé, sans résoudre le problème fondamental : l'absence de réflexion et la course à la vitesse au détriment de la qualité
