## Résumé de l'article

Roku a achevé la migration de l'ensemble de ses ressources de développement, dont la documentation, les applications exemples et les outils, de GitHub vers GitLab. Les référentiels conservent les mêmes noms, seule l'URL change de github.com/rokudev/ vers gitlab.com/rokudev/.

- Les liens dans la documentation officielle et les billets de blog ont été mis à jour automatiquement vers les nouvelles adresses GitLab
- Les développeurs doivent mettre à jour manuellement les URL stockées en favori, dans les clones Git existants, les submodules, les pipelines CI et les wikis internes
- Les référentiels indexés pour les systèmes de récupération d'informations ou assistants IA nécessitent une recrawl avec les nouvelles URL GitLab, y compris les chemins de fichiers bruts
- Les contributions à la documentation se font désormais via demande d'accès, fork et merge request sur le référentiel GitLab dev-doc

## Discussion sur Hacker News (140 commentaires)

**Avis positifs** :
- GitLab offre une meilleure expérience développeur, notamment avec un système CI/CD supérieur (pipelines parent-enfant, règles plus flexibles, meilleure intégration Kubernetes) comparé à GitHub Actions
- GitHub a connu de nombreuses pannes récentes (une dizaine en quelques mois) qui ont affecté les déploiements en production, tandis que GitLab peut être auto-hébergé pour éviter ces problèmes de fiabilité
- GitLab est mieux adapté aux organisations complexes avec des workflows plus sophistiqués, offrant une meilleure organisation hiérarchique des dépôts et des permissions plus intuitives
- L'auto-hébergement de GitLab (ou alternatives comme Forgejo) permet aux entreprises d'éviter les préoccupations concernant le scraping de code par l'IA et les violations de licences OSS
- Standardisation interne : Roku utilisant déjà GitLab internement, cette migration réduit la friction développement et simplifie les workflows entre les outils internes et externes

**Avis négatifs** :
- GitLab a aussi connu des pannes récentes et n'est pas immunisé contre les problèmes de fiabilité; l'auto-hébergement introduit ses propres défis (maintenance, sécurité, downtime de sauvegarde)
- Le changement de plateforme de CI/CD n'est pas trivial et nécessite une migration significative des pipelines, pas simplement un changement de miroir git
- L'auto-hébergement de services Git expose à des risques de sécurité élevés; maintenir la sécurité d'une instance à jour face aux nouvelles vulnérabilités est un travail continu et exigeant
- GitHub Enterprise et auto-hébergé existent depuis longtemps; les alternatives supposées supérieures ne sont pas nécessairement plus fiables à grande échelle que GitHub SaaS
- GitLab a également ajouté de nombreuses fonctionnalités superflues qui encombrent l'interface et éloignent l'utilisateur de l'essentiel du contrôle de version et de l'CI/CD
