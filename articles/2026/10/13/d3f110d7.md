## Résumé de l'article

Un développeur a construit marketyour.games, une application web commerciale complète (avec authentification, paiements Stripe, emails transactionnels), en utilisant le C et CGI — la même approche qu'en 1994 mais appliquée aux standards modernes. L'application fonctionne sur un unique binaire statiquement lié, une base SQLite, trois dépendances seulement, sans framework ni langage de templating.

- La pile BCHS (OpenBSD, C, httpd, SQLite) offre une architecture minimaliste : chaque requête lance un processus frais, les déploiements ne nécessitent que de remplacer un fichier, aucun redémarrage serveur.
- CGI n'est pas un framework à apprendre mais une interface HTTP standardisée depuis 2004 ; le coût de création de processus est devenu négligeable sur les noyaux modernes contrairement aux années 2000.
- Les avantages pour la sécurité incluent le sandboxing natif d'OpenBSD (pledge, unveil, chroot), une chaîne de dépendances réduite au minimum (C compiler + 3 bibliothèques), et une surface d'attaque bien inférieure aux écosystèmes modernes complexes.
- Le modèle simplifie le débogage (programme ordinaire exécutable depuis le shell), l'outillage mature (sanitizers, valgrind, gdb, ctags), et la maintenabilité grâce à l'absence de couches d'abstraction multiples.
- Les inconvénients incluent l'absence de framework/utilitaires pré-construits pour CGI, nécessitant du code maison pour gérer la sérialisation, l'authentification et d'autres fonctionnalités communes.

## Discussion sur Hacker News (159 commentaires)

**Avis positifs** :
- La simplicité de déploiement avec CGI (un seul fichier binaire, pas de redémarrage serveur) et l'absence de couches intermédiaires séduisent plusieurs commentateurs qui trouvent cette approche pragmatique et pertinente.
- Le choix de C offre des avantages concrets : pas de dépendances externes complexes, code qui tient dans la tête, exécutable unique et stable, ce qui contraste favorablement avec les chaînes de dépendances modernes.
- SQLite en mode WAL résout effectivement les problèmes de concurrence, et plusieurs utilisateurs confirment l'efficacité pratique de cette approche pour des applications à trafic modéré.
- Le projet inspire d'autres expériences similaires réussies (PHP+FastCGI, Lua+batteries, C++ avec WebAssembly) montrant que cette philosophie minimaliste fonctionne à l'échelle réelle.
- L'approche de renoncer aux frameworks modernes complexes pour une simplicité radicale résonne avec une tendance plus large de retour aux bases architecturales solides.

**Avis négatifs** :
- Écrire une application web sérieuse en C pose des risques sécurité majeurs : la gestion des chaînes de caractères est pénible et source de bugs, les vulnérabilités de sécurité sont quasi garanties face aux appels système directs.
- Forker un processus à chaque requête incombe une pénalité de performance (~8ms par requête) qui dépasse largement la surcharge de long-lived processes avec FastCGI ; cette approche n'échelle pas pour du trafic réel.
- La concurrence en C est fondamentalement complexe et douloureuse comparée aux abstractions modernes, rendant le débogage et la maintenance difficiles à long terme.
- Go, Rust ou même C++ offrent les mêmes bénéfices (binaire unique, absence de runtime, déploiement simple) tout en apportant la sécurité mémoire et une ergonomie bien supérieure pour écrire du code web fiable.
- Le billet lui-même souffre de problèmes d'accessibilité et de lisibilité (choix typographiques pauvres), et contient ironiquement du contenu généré par IA malgré la revendication de minimalisme.
