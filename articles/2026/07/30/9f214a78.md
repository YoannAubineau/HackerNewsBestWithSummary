## Résumé de l'article

SQLite est une base de données embarquée qui, correctement configurée, peut fonctionner efficacement en production sur des serveurs applicatifs. L'article détaille les techniques pour éliminer la latence réseau en exécutant SQLite localement et en optimisant ses mécanismes internes.

- Le Write-Ahead Logging (WAL) mode permet les lectures et écritures concurrentes en séparant les écritures dans un fichier .wal, éliminant le blocage mutual des lecteurs et rédacteurs
- La gestion des checkpoints (fusionnement WAL-base) doit être explicite en arrière-plan pour éviter que le fichier WAL croisse indéfiniment avec des lecteurs actifs
- SQLite impose un modèle à écrivain unique ; configure un busy_timeout et utilise BEGIN IMMEDIATE pour éviter les deadlocks et les erreurs SQLITE_BUSY
- L'optimisation mémoire passe par l'augmentation du cache_size (64 MB recommandé) et l'activation du memory-mapped I/O (mmap) pour transformer les lectures disque en opérations sur pointeurs
- Les couches VFS personnalisées (Litestream, LiteFS) permettent la réplication et la haute disponibilité dans les environnements cloud avec stockage éphémère

## Discussion sur Hacker News (76 commentaires)

**Avis positifs** :
- SQLite est viable en production pour de nombreux cas d'usage : applications sans des milliers d'utilisateurs simultanés, petits services sur VPS, déploiements edge et embarqués, où la simplicité opérationnelle compense les limitations.
- Les solutions de migration et d'alter table ont grandement amélioré récemment (SQLite 3.53+ supporte ALTER TABLE COLUMN NOT NULL, des outils comme sqlite-utils offrent des commandes robustes) et les workarounds existants (ajouter une colonne, utiliser des transactions pour les transformations) restent praticables.
- WAL mode + transactional DDL permettent des migrations sans downtime avec une sérialisation des écritures au niveau applicatif, et la durabilité peut être maîtrisée intentionnellement selon les besoins réels (par ex. LiteStream offre une fenêtre de perte de données plus courte que RDS).
- Les contraintes CHECK avec expressions JSON ou GLOB compensent partiellement les types limités; la cohabitation base de données/application dans le même versioning simplifie les déploiements pour applications single-tenant.

**Avis négatifs** :
- En production réelle, les limitations pratiques sont substantielles : ALTER TABLE est maladroit, les migrations doivent être copiées sur le serveur, les changements de schéma complexes nécessitent de créer/copier/renommer des tables (lourd comparé à Postgres).
- La concurrence en écriture reste problématique même avec WAL : les corruptions de base peuvent survenir avec plusieurs writers, nécessitant des verrous applicatifs pour un seul writer, ce qui élimine les bénéfices de concurrence et rend Postgres préférable.
- PRAGMA synchronous = NORMAL en WAL mode n'est pas réellement sûr : on peut perdre des transactions commitées en cas de crash, pas seulement les non-commitées, ce qui est souvent minimisé dans les documentations optimistes.
- Pour les applications exigeant durabilité, faible latence ET disponibilité (données critiques, multi-tenants non-trivial), recourir à LiteFS/LiteStream ajoute de la complexité qui annule les avantages de simplicité supposés par rapport à Postgres.
