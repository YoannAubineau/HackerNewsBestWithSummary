## Résumé de l'article

GitHub met en place une nouvelle fonctionnalité appelée « stacked pull requests » (pull requests empilées), qui permet de décomposer les grandes modifications en une série ordonnée de petites PR individuellement révisables et fusionnables.

- Les pull requests empilées divisent les changements complexes en couches indépendantes et révisables en parallèle, chacune ciblant la couche précédente
- Les équipes peuvent fusionner la pile entière en une opération unique, ou fusionner des couches individuelles progressivement; les couches restantes se rebaient automatiquement
- La fonctionnalité s'intègre nativement à GitHub et fonctionne avec l'interface web, le CLI GitHub, l'application mobile et les agents IA comme GitHub Copilot
- Elle est disponible en préview public sur tous les dépôts et bénéficie du support des file d'attente de fusion (merge queue) dans les semaines à venir
- Des témoignages de développeurs de Next.js, jQuery et TED soulignent que cela réduit la friction, accélère les revues et améliore la qualité du code

## Discussion sur Hacker News (109 commentaires)

**Avis positifs** :
- Améliore significativement l'expérience utilisateur pour les workflows de révision en découpant les grandes modifications en unités atomiques et revues indépendamment, avec la capacité de fusionner sélectivement même si certains PRs sont problématiques.
- Offre une bien meilleure ergonomie que le rebasing manuel et les branches ad-hoc : les développeurs n'ont plus besoin de basculer manuellement les branches cibles ou d'expliquer les dépendances entre PRs.
- Permet un CI/CD plus efficace : chaque PR de la pile peut être testée indépendamment et fusionnée en une seule opération atomique, réduisant les redéploiements coûteux comparé à des fusions individuelles.
- Fournit une API publique complète pour l'intégration avec des outils de merge queue et d'automatisation personnalisée, permettant aux organisations de construire leurs propres workflows.
- Populise enfin un workflow de développement connu et éprouvé (utilisé depuis des années chez Google, Facebook via Phabricator et Gerrit) auprès d'une large audience.

**Avis négatifs** :
- L'implémentation est boiteuse au lancement : les fusions de stacks avec squash merge sont cassées dans de nombreux cas, nécessitant une ré-approbation pour chaque PR, ce qui élimine le gain principal des PRs empilées.
- La révision par commit individuel dans GitHub reste clunky ; cette feature est davantage un contournement de l'absence d'interface pour reviewer proprement les commits plutôt qu'une solution à la racine.
- Le CLI tooling demande une connaissance fine de git rebase et ne signale pas les désynchronisations locales/distantes, rendant facile de se tirer une balle dans le pied.
- L'interface web reste très minimaliste (un simple dropdown) et n'offre qu'une petite fraction des fonctionnalités du CLI, rendant la découverte et l'adoption difficiles pour les utilisateurs occasionnels.
- Crée un risque organisationnel : les PRs dépendantes permettent de repousser indéfiniment la révision des PRs de base, et complexifie les tests puisque les codes non fusionnés s'accumulent.
