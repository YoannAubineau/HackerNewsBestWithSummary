## Résumé de l'article

Fil-C est un compilateur fork de Clang qui transforme du code C et C++ standard en code garantissant la sécurité mémoire. Il instrumental les opérations de pointeurs au niveau LLVM IR avec des « capacités invisibles » — des bornes stockées séparément — empêchant tout débordement de tableau, use-after-free ou accès mémoire non autorisé, tout en conservant une compatibilité extrême avec le code C/C++ existant.

- Le compilateur fonctionne en instruisant les opérations sur pointeurs LLVM avec des bornes invisibles (capacités) qui circulent avec les pointeurs mais restent inaccessibles à l'utilisateur, empêchant leur corruption.
- Environ 94 millions de lignes de code C/C++ (LibreOffice, GTK, CPython, Boost, etc.) ont été compilées avec succès avec des modifications minimales (0,1 % pour LibreOffice), montrant la compatibilité fanatique du projet.
- Le runtime utilise un garbage collector concurrent sans pauses plutôt qu'une gestion manuelle, garantissant qu'un use-after-free provoque toujours un panic au lieu d'une exploitation ; les appels système sont aussi filtrés et sécurisés.
- Fil-C ne supporte actuellement que Linux x86-64 et fonctionne environ 4 à 6 fois plus lentement que du C standard, mais élimine les échappatoires (pas d'équivalent Rust « unsafe »), rendant la pile logicielle entière sécurisée contrairement aux langages qui autorisent du code non sécurisé.

## Discussion sur Hacker News (171 commentaires)

**Avis positifs** :
- Fil-C offre une sécurité mémoire plus complète que Rust pour les appels système et l'interopérabilité : contrairement à Rust, les wrappers Fil-C autour de syscalls comme mmap garantissent la sécurité mémoire sans nécessiter d'audits de code unsafe.
- Fil-C permet de durcir le code C/C++ existant sans réécriture majeure, représentant une amélioration de sécurité pratique pour les projets legacy massifs (nginx, PostgreSQL, systemd, etc.).
- L'approche combine efficacement vérifications statiques et dynamiques : Fil-C peut servir de couche de sécurité supplémentaire autour du code unsafe Rust ou C, offrant une défense en profondeur.
- Les performances sont souvent meilleures que prévu pour certains usages (BLAKE3, xzutils montrent un surcoût proche de zéro après optimisations du compilateur).
- La garantie que les panics Fil-C indiquent clairement les violations de sécurité facilite le débogage comparé aux corruptions mémoire silencieuses de C/C++.

**Avis négatifs** :
- Fil-C n'élimine pas tous les vecteurs de sécurité : le compilateur ne peut pas protéger contre les modifications de pointeurs via /proc/self/mem, les accès bruts à /dev/mem, ou les races permettant de combiner des bits d'adresse et des capabilities non synchronisés, créant des accès cross-object inattendus.
- Les vérifications de sécurité sont exclusivement à l'exécution, non à la compilation, ce qui signifie que les bugs mémoire ne sont détectés que lors de l'exécution réelle du code problématique, laissant des vulnérabilités en production si non testées.
- Le surcoût de performance et mémoire (généralement 2-4x) rend Fil-C inutilisable pour les systèmes embarqués, les kernels, et les applications temps-réel où Rust excelle, limitant drastiquement les cas d'usage.
- Le marketing agressif du projet (framing oppositional envers Rust, affirmations exagérées de supériorité) crée de la confusion : les comparaisons 'Fil-C est plus sûr que Rust' occultem le fait que Rust peut aussi interdire l'unsafe avec #![forbid(unsafe_code)].
- Le projet reste immature et dépend largement d'une seule personne, soulevant des préoccupations sur la maintenabilité long-terme comparée aux écosystèmes Rust, Go, ou C# beaucoup plus établis et couverts par des audits de sécurité extensifs.
