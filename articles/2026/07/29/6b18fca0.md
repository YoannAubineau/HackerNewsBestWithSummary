## Résumé de l'article

Kimi Code propose deux modèles principaux—Kimi K3 et Kimi K2.7 Code—disponibles sous plusieurs identifiants de modèle. Le modèle K3-256k, nouvellement lancé, offre les mêmes performances que K3 (1M) dans une fenêtre de contexte de 256k tokens et consomme environ deux fois moins de quota, idéal pour les tâches quotidiennes et développement de petits fichiers (sans support vidéo).

- K3-256k est recommandé pour les questions-réponses, complétion de code et modifications de fichiers simples ; il n'est pas compatible avec les entrées vidéo
- Lors du passage de K3 (1M) à K3-256k, il faut d'abord compacter le contexte si celui-ci dépasse 256k, ou retirer les fichiers vidéo de l'historique
- L'accès aux modèles et fenêtres de contexte est déterminé par le plan d'abonnement ; les erreurs 401 surviennent quand les capacités demandées dépassent les droits du plan
- Pour basculer entre les modèles, utiliser l'identifiant de modèle exact (k3, k3-256k, kimi-for-coding, kimi-for-coding-highspeed) plutôt que le nom de version
- Il est recommandé de démarrer une nouvelle session lors du changement de modèle pour éviter l'invalidation du cache de contexte et réduire la consommation de tokens

## Discussion sur Hacker News (89 commentaires)

**Avis positifs** :
- 256k de contexte est généralement suffisant pour la plupart des tâches de codage, permettant des économies significatives de quota comparé au modèle 1M
- Le modèle Kimi K3 semble utiliser le contexte plus efficacement que Claude, même sur des sessions longues d'agent, grâce à son architecture et son harness optimisé
- Cette option offre une meilleure accessibilité tarifaire et répond aux besoins réels des utilisateurs qui ne saturent pas leur contexte, rendant les modèles IA progressivement des commodités accessibles
- Les utilisateurs peuvent commencer avec 256k et basculer vers 1M sans perdre le cache, offrant une flexibilité pratique sans surcoût caché

**Avis négatifs** :
- Sur des projets de refactoring ou nouvelles features conséquentes sur codebase moyenne, 256k sera insuffisant et obligera à compacter fréquemment, rendant les résultats inutilisables
- Ceci n'est qu'un changement au niveau API avec moins de contexte alloué, pas une véritable innovation du modèle lui-même
- L'implémentation par seuil dur (au lieu d'un gradient de prix progressif) est inefficace et peut inciter à des pratiques de gestion de contexte sous-optimales
- Doutes sur la transparence : impossible de vérifier directement si le modèle est quantifié ou véritablement complet, avec des craintes que certains fournisseurs tiers le quantifient secrètement
