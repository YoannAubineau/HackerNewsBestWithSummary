## Résumé de l'article

Au lieu de permettre tous les fichiers par défaut et d'en exclure certains, une approche alternative consiste à ignorer tous les fichiers par défaut et à n'autoriser explicitement que ceux que vous souhaitez suivre. Cela réduit le risque de commits accidentels de fichiers générés ou de configuration locale.

- La syntaxe repose sur `*` pour ignorer tout, puis `!` pour autoriser des fichiers spécifiques (par exemple `!*.go`, `!README.md`)
- Cette approche évite les commits involontaires de fichiers comme `.DS_Store`, `node_modules`, fichiers IDE ou variables d'environnement
- Particulièrement utile pour les projets contenant beaucoup de fichiers générés ou temporaires qui encombrent le référentiel local
- Pour vérifier si Git ignore correctement un fichier, utilisez la commande `git check-ignore -v chemin/du/fichier`
- Cette technique n'est pas appropriée pour tous les projets, mais représente une alternative à explorer selon le contexte

## Discussion sur Hacker News (173 commentaires)

**Avis positifs** :
- Ignorer les dotfiles par défaut (via `.*` en global .gitignore) prévient l'accumulation de fichiers de configuration personnels sans nécessiter de maintenance constante du .gitignore
- Une approche de type liste blanche force une réflexion délibérée sur ce qui mérite vraiment d'être commité, particulièrement efficace pour éviter les secrets et les artefacts non pertinents
- Utile dans les contextes spécifiques comme Docker (où ignorer tout par défaut réduit la taille des images) ou pour les projets avec de nombreux contributeurs juniors qui oublient naturellement d'ajouter des fichiers
- L'approche en whitelist détecte rapidement les fichiers manquants via des erreurs de compilation ou tests échoués, tandis que les fichiers secrets passent inaperçus en blacklist classique

**Avis négatifs** :
- Risque majeur : les développeurs oublient d'unignorer les fichiers qu'ils doivent commiter, causant des commits incomplets ou de la confusion sur branches, pire que d'ajouter des fichiers accidentellement
- Rend `git status` inutile puisque les fichiers ignorés n'apparaissent pas, perdant un outil d'alerte précieux pour détecter oublis ou changements inattendus
- Crée une fausse sécurité : les développeurs paresseux qui font `git add .` oublieront aussi d'unignorer les fichiers, tandis que ceux qui font attention n'ont pas besoin de cette approche
- Complexité accrue : nécessite de maintenir une liste explicite de fichiers autorisés qui changera avec chaque nouvel outil (Cursor, Claude, Zed...), contrairement aux gitignore templates standards ou aux gitignore globales personnelles
- La plupart des problèmes cités (OS, éditeurs) sont mieux résolus par un gitignore global personnel ou les templates GitHub plutôt que de refondre le paradigme pour tout le projet
