## Résumé de l'article

En Go, les chemins d'import pointent directement vers l'hébergeur git (notamment GitHub), ce qui crée un couplage du code à la plateforme. Migrer vers un autre hébergeur (GitLab, Azure DevOps) oblige à modifier le code source, rendant pratiquement impossible un changement de prestataire.

- Le problème : le code devient lié à GitHub ou tout autre hébergeur initial, créant une dépendance techniquement et économiquement coûteuse à briser
- La solution : utiliser un domaine personnalisé (ex. go.iain.rocks, go.uber.org) qui redirige les imports Go vers le vrai dépôt
- Avantage : modifier le lien de redirection ne change rien pour les utilisateurs finaux, qui gardent la même commande d'installation
- Implémentation : configurer un serveur web (Nginx) avec des métadonnées go-import et go-source pour que Go Tool trouve le dépôt réel
- Recommandation : tout développement commercial en Go devrait utiliser cette approche pour éviter un couplage injustifié à une plateforme d'hébergement

## Discussion sur Hacker News (95 commentaires)

**Avis positifs** :
- Un domaine personnalisé offre une indépendance vis-à-vis des plateformes d'hébergement (GitHub, GitLab, etc.) qui peuvent disparaître ou changer de politique, contrairement à Sourceforge ou Myspace
- Go permet facilement la gestion de vanity import paths via des templates Hugo ou des configurations nginx simples, donnant un contrôle total sur la résolution des dépendances
- Cette approche s'étend au-delà de Go : utiliser des domaines personnalisés plutôt que des URLs de forges évite les liens brisés lors de migrations de projets ou changements d'infrastructure
- Les domaines personnalisés permettent de pointer ultérieurement vers un registre d'artefacts ou un proxy privé, améliorant la fiabilité et la sécurité de la chaîne d'approvisionnement logicielle
- La pratique encourage une meilleure réflexion sur les dépendances et offre une garantie de continuité : un domaine personnel dure plus longtemps qu'une présence sur une plateforme

**Avis négatifs** :
- Ajouter une gestion de domaine aux développeurs open-source individuels crée une charge opérationnelle et une dépendance supplémentaire (renouvellement du domaine, serveur nginx); les domaines disparaissent quand on cesse de payer les factures, contrairement à GitHub
- Les migrations entre forges (GitHub vers GitLab) deviennent exponentiellement complexes avec les dépendances versionnées : chaque tag d'une version dépendante doit être migré séparément, créant des dizaines de tâches pour une simple migration
- Les URLs de forges dans le code source restent des références à une infrastructure abandonnée et la recherche/remplacement ne résout pas le problème pour les anciens commits, bisects cassés et l'impossibilité de compiler les anciennes versions
- GitHub étant presque permanent (contrairement aux domaines personnels qui disparaissent), et Google fournissant un proxy de cache centralisé pour Go, le risque réel d'indisponibilité est faible en pratique
- Le système d'import de Go basé sur les URLs crée un problème intrinsèque : si quelqu'un reprend un domaine expiré (comme des domaines supprimés par VeriSign), il hériterait silencieusement de packages entiers et pourrait introduire du code malveillant
