## Résumé de l'article

git-bug est un gestionnaire de bogues (bug tracker) entièrement intégré dans Git, permettant de gérer les problèmes directement dans un dépôt Git sans dépendre d'un service externe. Il fonctionne hors ligne, se synchronise via les remotes Git habituels, et ne pollue pas le projet en n'ajoutant aucun fichier.

- Fully distributed: synchronisation des bogues entre collaborateurs via `git bug push` et `git bug pull`, comme pour le code
- Multiple interfaces: CLI, terminal UI interactif (`git bug termui`), web UI locale (`git bug webui`), et API GraphQL
- Bridges avec autres trackers: import/export vers GitHub, GitLab, Jira et Launchpad via la commande `git bug bridge`
- Prévention du verrouillage: sauvegarde complète dans le dépôt Git, aucune dépendance à un service tiers
- Fast et offline-first: opérations rapides (milliseconde) et fonctionnement complet sans connexion réseau

## Discussion sur Hacker News (88 commentaires)

**Avis positifs** :
- Concept séduisant d'un système de suivi distribué, hors ligne et intégré à Git, répondant à un besoin longtemps ressenti (« pourquoi n'a-t-on pas eu ça plus tôt ? »)
- Approche pragmatique des conflits via CRDT pour les interactions sociales plutôt que résolution manuelle, préservant l'intention plutôt que la précision syntaxique
- Flexibilité du modèle de données : possibilité d'ajouter des opérations (assignation, etc.) et entités (PR, kanban) sans forcer chaque client à les implémenter
- Adoption croissante auprès d'acteurs majeurs (maintainers du kernel Linux, intégration b4/cgit), validant la pertinence de l'approche
- Avantage d'une portabilité totale du projet (code + tickets) sans dépendance à un service centralisé, et bénéfice d'accès hors ligne complet

**Avis négatifs** :
- Barrière d'accessibilité : nécessite une interface Web avec authentification OAuth pour être viable en pratique, sinon trop restrictif pour les utilisateurs non techniques et les rôles multiples
- Le nom « git bug » est limitant pour tracker des features et PR ; la limitation à deux états (ouvert/fermé) restrictive comparée aux trackers établis
- Problème technique non résolu : nécessité actuellement d'un agent SSH pour les opérations push/pull, incompatibilité avec les configurations SSH avancées (.ssh/config)
- Questionnement sur la pertinence fondamentale : pourquoi lier tickets et code en Git alors qu'ils sont naturellement décorrélés (vérification post-merge, cycles de vie indépendants) ?
- Historique d'échecs des trackers distribués précédents; la plupart n'ont jamais atteint l'ergonomie nécessaire, problème de conception inhérente plutôt que d'implémentation
