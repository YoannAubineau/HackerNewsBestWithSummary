## Résumé de l'article

Portal by Spotify est une plateforme permettant de créer et déployer des agents déclaratifs (appelés « modes ») qui exécutent des tâches spécifiques de manière isolée et économique. L'auteur décrit comment il a réduit sa consommation de tokens Claude de 90% en routant les tâches d'I/O gourmandes (lecture de fichiers, génération de code standard) vers des modèles légers comme Gemini 2.5 Flash, tout en réservant Claude pour le raisonnement complexe.

- Portal fournit des modes : agents sans infrastructure qui reçoivent des instructions, un modèle, des paramètres et des outils MCP, puis s'exécutent de façon éphémère (comparable à des Lambda serverless)
- L'auteur a créé deux modes : « bulk-reader » (analyse de fichiers multiples de façon ciblée) et « code-writer » (génération de boilerplate selon les patterns existants), tous deux utilisant Gemini Flash à très basse température (0.2)
- Un plugin Claude Code appelé « shunt » intercepte les appels d'outils (hooks PreToolUse) et bloque automatiquement les lectures de fichiers au-delà d'un seuil configurable (350 lignes par défaut), forçant la délégation au bulk-reader
- Les modes réduisent effectivement les coûts : test sur un monorepo Java montre ~90% d'économie de tokens pour les lectures, et le code généré ne transite jamais par Claude (zéro tokens de sortie)
- Les limites identifiées : impossible de déléguer l'édition fine (pas de numéros de ligne fiables), le raisonnement complexe ou la sécurité ; latence de 10-30 secondes par délégation et plafond de 30s par invocation pour les très gros fichiers

## Discussion sur Hacker News (124 commentaires)

**Avis positifs** :
- L'approche des sous-agents bon marché pour filtrer/scout le code pertinent avant lecture par un modèle coûteux est conceptuellement solide, comparable à un « Bloom filter LLM » qui guide sans décider
- Plusieurs utilisateurs confirment utiliser avec succès des workflows multi-modèles (orchestration par modèle coûteux, implémentation par modèles bon marché) pour réduire les coûts réels de manière significative
- Cette technique répond à un vrai problème : les modèles haut de gamme comme Opus ont tendance à sur-lire les fichiers, gaspillant tokens sur des lectures non productives
- Le paradigme fonctionne bien quand le modèle bon marché est cantonné à pointer des ressources (chemins de fichiers, plages de lignes) sans jugement sur le contenu

**Avis négatifs** :
- Aucune mesure de qualité du code généré ni taux de succès des tâches — seules les économies de tokens sont quantifiées, sans vérifier si la solution reste correcte
- L'approche n'est pas nouvelle : les harnesses Claude Code standard délèguent déjà aux sous-agents, et des outils comme Repoprompt, aider (repo map), ou même les instructions développeur existent depuis longtemps
- En pratique, le modèle coûteux doit souvent relire les fichiers lui-même pour valider ou corriger, annulant les économies promises — le problème de distribution du travail reste mal résolu
- L'article lui-même est rédigé en style IA avec tournures artificielles (« It's not X, it's Y », phrasés claudiens) et ignore complètement les vraies variables : coût output vs input, correctness, temps humain
- Les tokens input sont bon marché (~¼ du prix de l'output) ; le vrai gaspillage vient des re-lectures et retries en phase d'output, que cette approche n'adresse pas
