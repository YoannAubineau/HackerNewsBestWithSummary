## Résumé de l'article

Cet article propose une approche équilibrée pour utiliser les LLM sans sacrifier la qualité du code et le plaisir de programmer. L'auteur, programmeur Haskell, suggère de déléguer aux LLM les tâches rébarbatives (documentation, refactoring, recherche) tout en conservant personnellement l'écriture du code intéressant et complexe, plutôt que de laisser générer l'intégralité du code source.

- Confier aux LLM les tâches de nettoyage, de routine et de recherche (documentation, organisation de notes, vérification de listes de tâches), pas la conception ou l'écriture du code principal
- Maintenir une maîtrise de la base de code en codant soi-même : garder ses compétences, éviter une dégradation progressive vers une position de simple relecteur de code généré
- Mettre en place des cycles d'examen automatisés pour tout artefact produit par un LLM (code, plans, recherches) et exiger que l'agent explique ses sources avant d'accepter ses propositions
- Utiliser le workflow « planification collaborative, puis codage humain » plutôt que « planification, puis génération » : faire chercher à l'agent les zones à modifier et les pièges, puis coder soi-même
- Traiter l'épuisement des tokens comme une panne de service, non comme une limite d'usage ; préparer un travail hors ligne et toujours garder une liste de tâches planifiées pour continuer indépendamment

## Discussion sur Hacker News (266 commentaires)

**Avis positifs** :
- Les LLM peuvent libérer du temps pour les tâches vraiment intéressantes : architecture, design d'API, problèmes de fond, plutôt que boilerplate et tâches répétitives
- Pour les projets personnels et hobbyistes, les LLM réduisent drastiquement la friction et permettent de concrétiser rapidement des idées qu'on aurait sinon abandonnées
- Utilisés judicieusement (modèles rapides, révision attentive, garder le contrôle architectural), les LLM peuvent augmenter la productivité sans diluer la compréhension du code
- Les LLM excellent comme outils de vérification, test, debugging et comme documentation améliorée—permettant de se concentrer sur la logique métier plutôt que sur la recherche de documentation
- Plusieurs développeurs rapportent un meilleur équilibre travail-vie en déléguant les parties fastidieuses, tout en gardant les aspects créatifs et satisfaisants

**Avis négatifs** :
- Vibe-coding sans compréhension crée une dette technique massive, du code peu maintenable, et brise la chaîne d'apprentissage pour les juniors qui n'acquièrent jamais les bases
- Les LLM ne sont pas fiables : non-déterministes, imprévisibles, produisent du code différent chaque jour et cassent régulièrement des invariants existants à cause du contexte limité
- Atrophie cognitive dangereuse : déléguer systématiquement érode les capacités de penser et de concevoir ; les développeurs perdent leur mental model du système et deviennent dépendants
- Au travail, la pression à 'utiliser l'IA pour tout' tue l'engagement émotionnel envers le code et transforme les développeurs en 'conveyor belt operators' validant du slop, pas en artisans
- Comparaison avec les compilers est fausse : les compilers sont déterministes et vérifiables ; les LLM génèrent deux solutions complètement différentes pour le même prompt, rendant la confiance impossible
