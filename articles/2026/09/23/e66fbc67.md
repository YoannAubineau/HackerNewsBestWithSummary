## Résumé de l'article

Python Workers, le service permettant d'exécuter des applications Python dans l'environnement Cloudflare Workers (serveur edge computing), passe en disponibilité générale (GA). Python devient désormais un langage de première classe pleinement supporté, permettant l'intégration transparente avec tous les services Cloudflare (Workers AI, R2, D1, Hyperdrive, Durable Objects, etc.) et la compatibilité avec les frameworks populaires (FastAPI, Django, Flask).

- Support natif des liaisons Cloudflare : les développeurs Python peuvent maintenant utiliser directement les bindings Cloudflare sans conversion manuelle vers JavaScript, ce qui simplifie considérablement le code
- Frameworks web intégrés : FastAPI, Django et Flask peuvent s'exécuter nativement via des connecteurs ASGI/WSGI fournis par Cloudflare, éliminant le besoin de serveurs web séparés
- Accès aux bases de données : support complet de PostgreSQL et MySQL via Hyperdrive grâce à l'implémentation de syscalls de socket dans l'environnement WebAssembly
- Écosystème WebAssembly étendu : adoption de la norme PEP 783 (PyEmscripten) pour permettre aux mainteneurs de paquets de compiler facilement des packages Python pour WebAssembly
- Support IA natif : bibliothèques comme OpenAI, LangChain et MCP fonctionnent nativement, combinables avec Workers AI pour l'inférence GPU serverless

## Discussion sur Hacker News (41 commentaires)

**Avis positifs** :
- Cloudflare a considérablement amélioré les démarrages à froid et le support des paquets Python grâce à des snapshots mémoire et du sharding, rendant Workers plus pratique
- L'intégration de Pyodide et des contributeurs principaux (Hood Chatham, Gyeondjae Choi) a permis des avancées significatives, notamment avec le support JSPI pour les clients HTTP comme urllib3 et Requests
- Python Workers représente une continuation bienvenue d'une idée éprouvée (GAE, serverless) avec une meilleure exécution moderne et des améliorations continues
- La capacité à utiliser plusieurs versions de Python via des flags de compatibilité offre une certaine flexibilité, bien que limitée par les versions embarquées de Workerd

**Avis négatifs** :
- Les temps de démarrage à froid (~1 seconde rapporté) restent significativement plus lents que les alternatives concurrentes comme Wasmer (60ms), 16 fois plus rapide selon les benchmarks
- L'architecture liée à JavaScript/V8 limite les améliorations futures des temps de démarrage et crée des incompatibilités sémantiques entre le modèle async Python (lazy) et l'event loop JavaScript (eager)
- Les maintainers de projets upstream (urllib3) portent la charge de maintenance pour des backends expérimentaux (Emscripten) sans financement proportionnel, créant des risques de sécurité et d'incompatibilité
- Dépendance à une seule version globale de Pyodide/Workerd par version de Python limite la granularité du contrôle de version et complique l'adoption de nouvelles fonctionnalités
- L'overhead mémoire de Pyodide (10-50 MB supplémentaires estimés) consomme davantage d'allocation worker que d'autres runtimes
