## Résumé de l'article

FoxDev Studio est un nouvel environnement de développement qui permet d'exécuter les anciens projets Visual FoxPro (arrêté en 2007) sans conversion ni réécriture. Il recréé le runtime FoxPro en Rust et WebAssembly, en conservant la compatibilité avec le code existant tout en supprimant les limites 32-bit originales.

- Les projets, formulaires, tables et rapports FoxPro s'ouvrent directement depuis leurs fichiers d'origine sans migration préalable, avec un éditeur et débogueur intégrés qui reproduisent le comportement exact de Visual FoxPro 9
- Le runtime passe de 32 à 64 bits, éliminant les limitations de taille (tables et fichiers memo limités à 2 Go deviennent utilisables jusqu'à plusieurs centaines de gigabytes)
- Les appels système et bibliothèques d'automation (comme les fichiers .fll 32-bit) restent fonctionnels via un processus bridge dédié
- FoxScript ajoute des capacités modernes (lambdas, serveurs HTTP) au-dessus du langage FoxPro sans le modifier, permettant le développement web dans le même code
- Le projet est en développement actif avec des versions nightly publiées sur GitHub depuis la branche principale

## Discussion sur Hacker News (168 commentaires)

**Avis positifs** :
- Le projet répond à un besoin réel : des milliers d'entreprises font encore tourner des applications VFP critiques (certaines générant des centaines de millions de dollars annuels), sans alternative viable de migration
- La nostalgie et l'appréciation pour l'ergonomie et la productivité de VFP : nombreux développeurs soulignent que VFP offrait une véritable intégration (IDE, designer, débogueur, générateur de rapports) que les outils modernes n'égalent pas
- L'accès démocratisé aux outils : VFP et ses prédécesseurs permettaient aux experts métier et développeurs juniors de créer des solutions professionnelles rapidement, sans expertise enterprise
- La supériorité de la conception pour certains cas d'usage : les applications VFP filaires étaient efficaces pour les CRUD métier simples, les rapports complexes et l'accès aux données locales optimisé pour les E/S réseau

**Avis négatifs** :
- Problèmes de sécurité architecturaux majeurs : le modèle DBC (Database Container) permet à n'importe quel utilisateur avec accès fichier d'exécuter du code arbitraire via les procédures stockées en texte clair, et les fichiers DBF partagés n'offrent aucun contrôle d'accès
- Les applications VFP n'évoluent pas bien : impossible de gérer l'accès multi-utilisateurs via réseau sans corruption de données, déverrouillage de fichiers problématique, et les primitives de la plateforme deviennent insuffisantes quand les besoins grandissent
- Le projet lui-même présente des signaux d'alerte : site 'vibecoded' avec texte généré par IA, domaine enregistré il y a 7 heures, un seul commit récent, et l'auteur admet avoir utilisé Claude pour la conception, soulevant des doutes sur la fiabilité pour des données sensibles
- La migration reste la meilleure option : les experts s'accordent qu'une réécriture vers une architecture client/serveur appropriée (SQL Server, PostgreSQL) élimine les problèmes de verrouillage et offre une sécurité véritable, malgré le coût initial
