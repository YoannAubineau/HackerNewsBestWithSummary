## Discussion sur Hacker News (239 commentaires)

**Avis positifs** :
- Les fuzzers, qu'ils soient créés par IA ou non, restent précieux car ils produisent des cas de test reproductibles et révèlent des bugs dans les angles morts des approches existantes.
- L'utilisation d'IA pour coder des outils (fuzzer, scripts de test) peut être rentable : on paie une fois en tokens pour un outil permanent, contrairement aux appels répétés.
- Même si le bug était trivial, l'approche méthodologique (TDD, testing battery, usage de plusieurs modèles) et la pipeline de CI/CD maison sont pertinents et démontrent une ingénierie sérieuse.
- L'approche d'IA pour trouver et vérifier des bugs est complémentaire : utiliser l'IA pour la détection, puis les humains pour valider et choisir le meilleur correctif limite les erreurs.
- Les systèmes de types forts (Haskell, langages avec types dépendants, Ada) pourraient prévenir entièrement ce type de bug et devraient accompagner le code généré par IA.

**Avis négatifs** :
- Ce bug spécifique était déjà connu depuis 2024 (trouvé par OSSFuzz) : deux mois et 1100+ commits pour redécouvrir la même vulnérabilité remet en question l'utilité réelle.
- Ce n'est pas un vrai bug de sécurité exploitable, juste un crash sur données invalides (DoS trivial) affectant un codec peu utilisé, insuffisant pour justifier le battage médiatique autour de l'IA.
- Le code et la documentation du fuzzer ressemblent à du 'AI slop' inefficace : la complexité générée par IA masque souvent ce qui pourrait être simple et clair si écrit à la main.
- Faire en sorte que l'IA écrive du code pour vérifier l'IA crée une spirale de dépendance problématique : on perd la compréhension du code et on accumule dette technique et bugs non détectés.
- L'accumulation de volume sans compréhension architecturale (comme l'a montré l'anecdote du développeur junior) produit du code fragile qu'on n'ose jamais toucher, régression par rapport aux bonnes pratiques de génie logiciel.
