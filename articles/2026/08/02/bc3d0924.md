## Résumé de l'article

Le groupe de travail Go Collections propose d'ajouter plusieurs structures de données de collection génériques à la bibliothèque standard à partir de Go 1.28. Ces nouvelles structures (Map, Set, Heap génériques) visent à offrir une ergonomie comparable aux types intégrés de Go, en s'appuyant sur les génériques introduits en Go 1.18 et les itérateurs de Go 1.23.

- Les propositions incluent container/hash.Map et container/hash.Set (utilisant des fonctions de hachage personnalisées), container/set.Set (pour les éléments comparables), container/ordered.Map (basée sur un arbre binaire équilibré) et container/heap/v2.Heap (API générique pour les tas binaires).
- Les nouvelles API utilisent la polymorphie bornée récursivement pour définir des interfaces de contraintes abstraites non exportées (_AbstractCollection, _AbstractMap, _AbstractSet) permettant des opérations génériques cohérentes.
- Les méthodes de mutation retournent autant d'informations que possible (changement de taille, valeur précédente) pour éviter les recherches répétées ; les opérations d'algèbre ensembliste comme Union proposent à la fois une variante fonctionnelle (retourne un nouveau set) et une variante mutante suffixée -With.
- Les implémentations initiales visent la clarté et les performances asymptotiques plutôt que l'optimisation des constantes, laissant la place à des améliorations futures.
- Le package container/set.Set basé sur map[T]struct{} devrait devenir le standard pour les nouveaux ensembles en Go, remplaçant les conventions legacy map[T]bool et map[T]struct{}.

## Discussion sur Hacker News (189 commentaires)

**Avis positifs** :
- Les collections génériques sont long à venir mais nécessaires : après des années sans elles, des millions de lignes de code ont dû contourner ce manque, créant de la dette technique que ces bibliothèques aideront à résoudre
- Go conserve sa philosophie en évitant la complexité : contrairement à C++ ou Java, l'équipe Go a pris 10 ans pour concevoir des génériques qui n'impactent pas les temps de compilation ni la lisibilité du code ordinaire
- Ces ajouts rendent le langage plus pratique sans le forcer : les génériques et itérateurs restent optionnels et peu utilisés dans le code applicatif courant, concentrant surtout les bénéfices pour les auteurs de bibliothèques
- Go se rapproche enfin des langages modernes : des ensembles, des files de priorité et d'autres structures de base manquaient depuis le début, et leur ajout graduel montre une évolution raisonnable plutôt qu'une capitulation

**Avis négatifs** :
- Les décisions de conception précoces rendent l'intégration difficile : l'impossibilité de définir des méthodes sur les types externes limite l'écriture de code générique compile-time convenable, forçant des contournements avec type-switching à l'exécution
- Go sacrifie son unicité en empilant des features : chaque addition érode la simplicité qui faisait la force du langage, créant progressivement une complexité comparable à C++ ou Java sans résoudre les vrais problèmes
- Des années de ressentiment justifié : l'équipe Go a longtemps défendu ardemment l'absence de génériques, forçant des développeurs à écrire du code maladroit pendant des années, avant d'enfin les ajouter sans véritable reconnaissance de cet échec
- Go n'était jamais vraiment simple dans la pratique : les footguns comme les paniques sur cartes nil mais pas sur slices nil, l'absence de discriminated unions, et la gestion d'erreurs verbeuse contredisent la promesse de simplicité
