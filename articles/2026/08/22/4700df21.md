## Résumé de l'article

OpenTelemetry est un projet CNCF visant à fournir une instrumentation d'observabilité (traces, métriques, logs) vendor-agnostique et standardisée. Bien que techniquement ambitieux, le projet fait face à des défis structurels qui ralentissent le déploiement de nouvelles fonctionnalités.

- Le projet souffre d'une concentration excessive de mainteneurs : certains SDKs (PHP, Ruby) sont maintenus par seulement 2-3 personnes, ce qui crée un goulot d'étranglement ; les SDKs Go et .NET sont plus sains mais restent sous-dotés comparés à des projets CNCF comme Envoy ou Prometheus
- L'architecture en deux niveaux (Core stable + Contrib communautaire) crée une friction : les utilisateurs évitent les features marquées "Experimental" faute d'accès clair, ralentissant le cycle de rétroaction
- Le processus de validation des nouvelles features (OTEP → Spécification → Conventions sémantiques → Implémentation SDK → Contrib) impose des verrous de stabilité qui découragent les discussions constructives et gelent l'évolution
- Les mainteneurs sont employés par des entreprises vendors (leur employeur), créant une tension entre contributions bénévoles impossibles à grande échelle et attentes imposées par les organisations parentales
- Parmi les solutions proposées : un niveau Beta intermédiaire limité dans le temps (12 mois minimum) pour exposer les features en cours de validation, plus de transparence sur les inégalités de maintenance entre SDKs, et un appel explicite à recruter plus de mainteneurs indépendants

## Discussion sur Hacker News (99 commentaires)

**Avis positifs** :
- OTel offre une standardisation ouverte qui évite l'enfermement propriétaire des vendeurs et permet à quiconque de créer des sources/destinations compatibles via OTLP
- Les alternatives simples (Prometheus, Jaeger seul) ont leurs propres limites ; OTel reste la meilleure option pour mixer plusieurs destinations d'observabilité (Sentry, Langfuse, Datadog, etc.)
- Le projet est viable et fonctionnel dans de nombreux cas ; les problèmes critiques soulevés sont souvent surestimés ou résolubles avec une meilleure compréhension du design

**Avis négatifs** :
- Performance insuffisante : surcharge CPU/RAM substantielle, pénalités importantes de démarrage à froid en serverless, forçant une double infrastructure de collecteurs gateway/edge
- Sur-ingénierie majeure avec abstractions excessives, API complexe, changements incompatibles fréquents en 0.x, et mauvaise documentation avec exemples contradictoires ou erronés
- Standardisation prématurée : les conventions sémantiques sont encore expérimentales ; chaque vendor implémente OTel partiellement en alpha/beta après des années, et l'instrumentation reste nécessaire pour besoins métier spécifiques
- Manque de flexibilité opérationnelle : auto-instrumentation casse les apps non-triviales ; impossible de caler dans des processus de démarrage complexes ou architectures non-standard (serverless durable, workers distribués)
