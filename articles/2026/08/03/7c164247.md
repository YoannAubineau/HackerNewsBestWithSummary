## Résumé de l'article

Kakehashi est un outil expérimental qui permet d'exécuter des binaires macOS ARM64 nativement sur des systèmes Linux aarch64 sans émulation JIT. Il charge les exécutables Mach-O de Darwin, mappe une libSystem isolée, traduit les appels système BSD, et supporte des outils réels comme clang, 7-Zip, curl avec support des threads.

- Fonctionne via une interface CLI (commandes `kh install`, `kh run`) ; compatible Docker, Colima et UTM sur Linux aarch64
- Supporte des applications complexes : 7-Zip avec compression multi-thread, curl avec HTTP/HTTPS, et des binaires clang ; file system bridgé via `/Volumes/linux/`
- Performance : gain de vitesse dépend de la charge (×1.1–1.2 sur compression légère, ×5–10 sur opérations intensives de syscalls) ; l'objectif est les runners CI bon marché plutôt que la vitesse native
- Cas d'usage limités : exécutables CLI purs sous libSystem freestanding ; ne supporte pas l'interface graphique, la signature de code, ou la notarisation (macOS natif requis)
- Nécessite Rust 1.88+, Linux aarch64, et pages de 4 KiB (conteneurs) ou 16 KiB (Asahi) ; licencié Apache 2.0

## Discussion sur Hacker News (38 commentaires)

**Avis positifs** :
- Le projet s'inspire légitimement de travaux antérieurs (Darling) sans copier directement le code, avec une architecture fondamentalement différente (userspace pur vs kernel-level) et un langage différent (Rust vs C/ObjC)
- Les prototypes fonctionnels (7-Zip, curl, Git) démontrent la viabilité technique, même si lents; le plan d'optimisation est clair et le projet accueille favorablement l'audit du code
- La vision long terme est comparable au succès de Wine/Proton pour Windows : un cadre léger et redistributable pourrait habiter un créneau important pour les outils CLI et les workflows de développement
- Les cas d'usage concrets (build iOS sur ARM Linux, environnements CI/CD) motivent fortement le développement et trouveraient un public

**Avis négatifs** :
- La surface d'ABI macOS est énorme et change annuellement; historiquement, les taux de succès pour ce type de projet sont exceptionnellement bas, sauf si les LLMs changent le calcul
- Les applications non-jeux (productivité) reçoivent moins de support que les jeux sur Wine/Proton; les outils Xcode et Homebrew changent régulièrement et cassent les dépendances même sur macOS natif
- Le projet reste très précoce : stabilité non garantie pour Git, 5,2x ralentissement pour 7-Zip, et la cible mouvante de Xcode/Homebrew rend les promesses d'une portabilité complète hautement spéculatives
- Même l'approche userspace de Darling (découverte après le lancement) réduit une différence architecturale majeure revendiquée; l'utilisation d'LLMs rend impossible une vérification absolue de l'absence de contamination conceptuelle du code
