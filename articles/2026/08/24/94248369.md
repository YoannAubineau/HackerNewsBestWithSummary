## Résumé de l'article

Le fichier agent.md est un document injecté dans le prompt des IDE assistés par IA (comme Claude Code ou Gemini) pour codifier les préférences de style et les bonnes pratiques. L'auteur a découvert que les LLM généraient initialement du code de mauvaise qualité, mais qu'en itérant avec des outils agentiques et en consolidant ses retours répétitifs dans agent.md, la qualité du code produit s'est rapprochée de celle d'un développeur expérimenté.

- Le fichier agent.md contient des règles concrètes sur le style de code : noms de fonction courts, pas de constantes magiques, enums au lieu de booléens, commentaires minimalistes expliquant le *quoi* et le *pourquoi*
- Des principes architecturaux figurent dans le document : respect des couches d'abstraction, encapsulation des détails bas niveau, limitation de la visibilité des membres, éviter les modifications inutiles de code existant
- Des conventions de commit messages y sont définies (7 règles formelles : limite de 50 caractères, mode impératif, séparation sujet/corps)
- La technique du test-first pour les bug fixes est documentée dans agent.md
- L'approche limite l'effet de « context dilution » identifié dans la recherche académique (Lost in the Middle paper), où les LLM prêtent moins d'attention aux instructions au milieu du contexte

## Discussion sur Hacker News (20 commentaires)

**Avis positifs** :
- Les linters et règles déterministes (comme ASD-STE100 Simplified Technical English) sont plus efficaces que de compter sur les agents pour respecter des conventions de code
- La formulation positive (dire ce que faire plutôt que ce à éviter) guide mieux les LLM que les prohibitions, qui risquent de renforcer les comportements indésirables
- Les commentaires générés par les LLM sont souvent confus, avec des métaphores inventées au lieu de termes techniques standards ; un contrôle strict améliore la qualité du code
- Les règles de convergence (succès, progression significative, ou arrêt honnête) préviennent l'accumulation infinie de patchs et de dettes techniques
- La documentation de haut niveau (glossaire, aperçu du design) est plus utile que des commentaires au niveau du code pour comprendre les systèmes complexes

**Avis négatifs** :
- Beaucoup de recommandations de l'article sont redondantes : les LLM connaissent déjà des bonnes pratiques comme utiliser les switch/match exhaustifs
- Imposer des noms de fonction courts (< 30 caractères) est arbitraire et peut produire des abréviations illisibles et confuses, comme le montrent les noms longs mais descriptifs en Rust ou Objective-C
- Les LLM traitent les directives comme des suggestions, non comme des ordres absolus ; contrôler la génération de commentaires est difficile et varie selon le modèle
- Les LLM sont mauvais pour générer des diagrammes ASCII ; demander cette fonctionnalité dépasse les capacités actuelles
- La mesure réelle de l'efficacité de ces rules reste floue : vaut-il mieux laisser l'agent itérer/auto-reviewer plutôt que de polir chaque détail ?
