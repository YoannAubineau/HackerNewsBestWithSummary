## Résumé de l'article

SELF (Structured Executable & Linkable Format) est un prototype qui remplace le format ELF traditionnel par une base de données SQLite. Les exécutables SELF sont des fichiers SQLite marqués avec un identifiant spécifique, exécutables directement via binfmt_misc, qui stockent les en-têtes de programme et la table des symboles sous forme de tables.

- Un fichier SELF nécessite deux tables principales (segments pour l'image à charger, symbols pour les symboles) plus des tables optionnelles pour les métadonnées ; supprimer les tables optionnelles revient à faire un strip, réalisable en une transaction SQL
- Les outils traditionnels (ldd, nm, readelf, strip) se réduisent à des requêtes SQL ; les modifications comme strip deviennent des DELETE au lieu de manipulations binaires fragiles
- Un fichier SELF est environ deux fois plus volumineux qu'un ELF équivalent, mais ce surcoût disparaît à l'échelle : 723 exécutables et 400 bibliothèques compilés dans une seule base occupent 611,9 MiB contre 644,4 MiB en ELF, grâce à la déduplication naturelle des bibliothèques partagées
- La liaison dynamique fonctionne soit via un audit library interceptant les appels ld.so pour les convertir en requêtes SQL, soit avec un éditeur de liens entièrement écrit en SQL (self-ld)
- Des fermetures (closures) regroupent un binaire et ses dépendances transitives dans une seule base de données, éliminant l'ambiguïté des noms de bibliothèques ; LD_PRELOAD devient une ligne de table modifiable par transaction

## Discussion sur Hacker News (25 commentaires)

**Avis positifs** :
- L'idée de combiner un exécutable et une base de données est brillante et ouvre des perspectives intéressantes : elle pourrait remplacer des formats comme AppImage de manière plus efficace
- Le concept démontre qu'ELF et d'autres formats exécutables sont déjà des bases de données relationnelles, ce qui remet en question la séparation traditionnelle entre code et données
- Les tables virtuelles SQLite permettent de monter n'importe quoi (système de fichiers, etc.) en tant que base de données SQL, ce qui est impressionnant et utile
- L'article inspire et pousse à explorer des idées iconoclastes ; les critiques académiques négatives ne doivent pas décourager l'innovation en programmation
- Le travail de l'auteur est admiré pour sa créativité récente et démontre qu'il existe encore des innovations possibles dans des domaines apparemment établis

**Avis négatifs** :
- L'absence de mmap est un problème sérieux : cela cause une duplication en mémoire et empêche un déswap efficace par le noyau, augmentant significativement l'usage RAM
- L'affirmation que SQLite interne automatiquement les chaînes de caractères est incorrecte ; SQLite ne le fait pas par défaut, il faut le faire manuellement
- Les antivirus peuvent devenir suspects quand une application se modifie elle-même, créant des problèmes opérationnels ; il est généralement plus pratique de conserver les données dans des fichiers séparés
- C'est une réinvention de la roue : les mainframes, les Tcl starpacks, RedBean et d'autres projets ont déjà exploré ces concepts bien avant
- Le format ELF est déjà très serré et difficile à modifier ; proposer une conversion ELF ↔ SELF plutôt qu'une refonte directe serait plus pragmatique
