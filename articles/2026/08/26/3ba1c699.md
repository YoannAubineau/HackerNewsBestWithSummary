## Résumé de l'article

SELF est un format où un programme exécutable est stocké comme base de données SQLite, permettant au programme en cours d'exécution de lire et modifier son propre état transactionnellement. self-httpd est un serveur web de preuve de concept qui démontre ce concept : un seul fichier contient le programme, le site web, les routes et tous les journaux de visiteurs, le tout interrogeable via SQL.

- Le format SELF utilise binfmt_misc pour exécuter un interpréteur qui mappe les lignes de la table segments et saute au point d'entrée ; le programme accède à lui-même via argv[0] et peut ouvrir sa propre base de données SQLite
- L'application stocke tout son état (visiteurs, boutons pressés, contenu) dans le même fichier SQLite que le programme, avec support complet des transactions ACID et des ROLLBACK
- Le déploiement se réduit à copier un seul fichier et effectuer une migration de données via INSERT...SELECT ; les mises à jour de contenu en direct ne nécessitent ni redémarrage ni rechargement
- Tous les outils SQLite existants (sqldiff pour l'audit, FTS5 pour la recherche en texte intégral) deviennent disponibles gratuitement pour l'application
- Le format offre une alternative plus simple que redbean (webserver Actually Portable Executable) en utilisant la base de données comme conteneur plutôt qu'une archive ZIP

## Discussion sur Hacker News (77 commentaires)

**Avis positifs** :
- Concept brillant et créatif : effondrement élégant de multiples domaines (code, données, état) dans une seule abstraction queryable, comparable aux images Lisp/Smalltalk ou à OS/400
- Avantages pratiques concrets : déploiement simplifié en fichier unique, transactionnalité ACID pour les migrations d'état, possibilité de multi-arch fat binaries, interrogation du code par SQL
- Résonance historique positive : redécouverte de concepts anciens (starkit, tclkit, CouchDB, SQLar) qui méritaient une meilleure adoption, particulièrement pertinent pour les compilateurs/linkers et les symboles de débogage
- Déploiement hermétique attrayant : collapsus d'une distribution complète plus tous les états applicatifs en un seul fichier, élimination du besoin de /var/, /tmp/, /home/
- Excellence académique : démonstration remarquable de liberté créative et capacité à réinterpréter les formats binaires, incarnant l'esprit de projets comme PoC || GTFO

**Avis négatifs** :
- Risque sécurité critique : tout bug SQL injection devient RCE immédiatement ; un binaire internet-facing auto-modifiable crée une vulnérabilité inacceptable sans ACL SQLite (actuellement absent)
- Problèmes architecturaux non résolus : plusieurs instances du même binaire ne peuvent partager l'état sans collision ; données utilisateur stockées dans le binaire plutôt que séparées crée des complications pour multi-utilisateur et portabilité
- Limites opérationnelles : perte accidentelle du binaire = perte simultanée du code et des données ; impossible de stocker l'état si le fichier est en emplacement privilégié ; coût de performance potentiel vs. approches établies
- Philosophie opposée au design immutable : stockage d'état mutable à l'exécution contredit les bonnes pratiques modernes (NixOS, distributions immutables) ; préférence arguée pour binaires read-only avec répertoires d'état séparés
- Peu de valeur unique SGBD sur API filesystem traditionnel : la plupart des bénéfices (transactionnalité, schémas) deviennent secondaires si seules les interactions filesystem sont autorisées ; comparaison avec qcow2 ou Format.POSIX classiques
