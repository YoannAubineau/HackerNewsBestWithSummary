## Résumé de l'article

Cette page documente les capacités interactives qu'HTML peut fournir nativement sans recourir à JavaScript, notamment via les attributs popover, dialog, details, command et les nouveaux types d'entrée. L'auteur signale que certaines implémentations navigateur restent incomplètes ou posent des enjeux d'accessibilité.

- **Popovers et dialogues** : les attributs `popover` et `popovertarget` permettent d'afficher des fenêtres contextuelles sans gestion du z-index ni JavaScript ; l'élément `<dialog>` offre une alternative pour les modales
- **Accordéons HTML** : l'attribut `name` partagé sur plusieurs éléments `<details>` crée automatiquement un groupe exclusif où ouvrir l'un ferme les autres
- **Commandes sans script** : les attributs `command` et `commandfor` permettent à plusieurs boutons HTML de contrôler un même élément (popover, dialog) sans code JavaScript
- **Chargement différé et révélation** : `loading="lazy"` sur les images retarde leur chargement jusqu'à proximité de la fenêtre d'affichage ; `hidden="until-found"` masque du contenu jusqu'à sa recherche ou sa navigation par fragment
- **Éléments de formulaire enrichis** : les types `<input>` couleur, plage, date et l'élément `<datalist>` offrent des sélecteurs natifs, mais leurs implémentations navigateur sont encore inégales sur le plan de l'accessibilité et des styles par défaut

## Discussion sur Hacker News (107 commentaires)

**Avis positifs** :
- HTML a considérablement progressé et permet désormais de créer des interfaces interactives (dialogues, popovers, accordéons, détails groupés) sans JavaScript, réduisant la complexité et améliorant les performances.
- Les nouvelles fonctionnalités HTML offrent une meilleure expérience utilisateur native, une accessibilité supérieure et une cohérence cross-navigateur comparées aux implémentations JavaScript ad hoc (ex: gestion automatique des couches de stacking pour les popovers imbriqués).
- Les pages rendues côté serveur avec HTML sémantique se chargent plus rapidement, fonctionnent sans JavaScript (NoScript), favorisent les signets fonctionnels et échappent aux problèmes UX des applications monopages.
- Certains cas d'usage spécifiques comme les tableaux avec tri simple, les formulaires nommés correctement et les contenus cachés jusqu'à découverte par recherche (hidden-until-found) s'avèrent pleinement fonctionnels en HTML pur.
- Les contraintes de développement sans JavaScript favorisent des choix architecturaux plus réfléchis et performants, comme démontré par textlog.cc qui réussit à offrir une riche interactivité en HTML seul.

**Avis négatifs** :
- Datalist ne constitue pas une véritable solution pour les comboboxes exigeants : il ne valide pas l'entrée utilisateur, manque de filtrage flou, de gestion des fautes de frappe et reste partiellement buggé avec un support navigateur inégal (absent en Firefox pour certains cas).
- Ces nouvelles fonctionnalités HTML n'offrent que des solutions « presque suffisantes » : les sélecteurs de date/heure sont limités, les contrôles de dialogue manquent d'inertie, et le positionnement des popovers demeure complexe malgré l'anchor positioning.
- Le support navigateur fragmenté rend l'adoption délicate : les navigateurs implémentent différemment ces fonctionnalités (particulièrement Safari et Chrome), les LLMs ont peu de données d'entraînement sur ces nouveaux standards, et la compatibilité multi-navigateur augmente la charge de travail.
- HTML n'a jamais été conçu pour les applications complètes, only pour la mise en page de documents ; vouloir tout faire en HTML pur revient à utiliser un outil inadapté et limite l'innovation face à des besoins réels de triage multi-colonnes, recherche côté client et animations complexes.
- Les popovers et dialogues restent une anti-pattern en UX : ils interrompent et bloquent le contenu, poussant les utilisateurs à quitter le site immédiatement, sauf dans des cas spécifiques comme les confirmations sur tableau de bord.
