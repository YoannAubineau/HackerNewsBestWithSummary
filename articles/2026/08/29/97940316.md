## Résumé de l'article

Le SDK OpenAI Python migre vers HTTPX2 pour ses clients HTTP synchrones et asynchrones. HTTPX2 s'installe automatiquement avec openai et remplace le paquet httpx précédent. Cette migration apporte des changements dans la gestion des certificats TLS, les transports personnalisés et les dépendances externes.

- HTTPX2 utilise le magasin de confiance du système d'exploitation au lieu de certifi, ce qui peut nécessiter d'installer les certificats CA du système ou de configurer explicitement un bundle de certificats via SSL_CERT_FILE ou SSL_CERT_DIR
- Les applications sans client HTTP personnalisé continuent de fonctionner sans modification ; les appels API, modèles de réponse, authentification et délais d'expiration restent inchangés
- Les objets spécifiques à HTTPX doivent être remplacés par leurs équivalents HTTPX2 (httpx.Client → httpx2.Client, httpx.Request → httpx2.Request, etc.)
- Le SDK fournit des helpers comme DefaultHttpx2Client et DefaultAsyncHttpx2Client qui préservent les configurations recommandées pour les délais d'expiration et les pools de connexion
- Les applications utilisant RESPX ou d'autres intégrations HTTPX doivent migrer vers des versions compatibles HTTPX2 ; un support hérité de HTTPX peut être temporairement maintenu avec cast(Any, ...) pour les tests

## Discussion sur Hacker News (93 commentaires)

**Avis positifs** :
- Migration vers HTTPX2 offre des avantages techniques : utilisation du magasin TLS du système d'exploitation au lieu de certifi, meilleur support async, API plus propre et composable que requests, et compatible avec les transports WSGI/ASGI pour les tests
- HTTPX2 bénéficie d'un soutien institutionnel fort (Pydantic) et d'une gouvernance communautaire active, contrairement au projet HTTPX original devenu inactif et fermé
- Cette approche de migration via documentation facilite l'adoption par d'autres projets et représente une bonne pratique pour les changements de dépendances
- Le retrait de certifi résout un problème longstanding : son intégration dans de nombreuses dépendances crée des complications pour les environnements avec certificats CA personnalisés (réseaux d'entreprise)

**Avis négatifs** :
- Le changement de l'utilisation de certifi vers le magasin TLS du système peut être un breaking change problématique pour les environnements d'entreprise utilisant des CA internes
- La situation fragmentée (HTTPX original fermé, HTTPX2, HTTPXYZ, alternatives comme niquests ou pyqwest) reflète une gouvernance confuse et crée de la confusion dans l'écosystème Python
- HTTPX2 ne supporte pas encore HTTP/3, rendant le choix moins futuriste que d'autres alternatives émergentes
- Certains arguments questionnent la pertinence même du débat : les SDKs sont des wrappers simples autour de REST+JSON, utilisables ou contournables facilement sans dépendre de ces choix techniques
- Les alternatives (niquests, pyqwest) montrent des performances supérieures (jusqu'à 4.8x plus rapide dans certains cas) et offrent des API compatibles sans rupture majeure
