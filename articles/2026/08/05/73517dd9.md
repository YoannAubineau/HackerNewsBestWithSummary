## Résumé de l'article

Le 4 août 2026, des attaquants ont compromis le compte GitHub du mainteneur de Keyv, une bibliothèque de stockage clé-valeur téléchargée 127 millions de fois par semaine, et ont injecté un ver voleur de credentials dans toute la famille de paquets. L'attaque a touché au moins 444 paquets avec plus de 2 milliards d'installations mensuelles combinées, y compris flat-cache, file-entry-cache, cacheable et d'autres utilitaires de cache largement utilisés.

- Les attaquants ont poussé directement des fichiers malveillants (setup.mjs et Math_Symbol.js) vers la branche principale et publié immédiatement de nouvelles versions avec des signatures GitHub Actions valides.
- Le malware exécute automatiquement un script au moment de l'installation (via preinstall) qui télécharge le runtime Bun et exécute une charge utile volant les credentials : tokens npm et GitHub, clés AWS, secrets Kubernetes, tokens Vault, ainsi que fichiers de configuration et clés privées via analyse filesystem.
- Les données volées sont chiffrées avec une clé RSA de l'attaquant et exfiltrées vers des dépôts GitHub publics ayant « Shai-Hulud: Here We Go Again » dans leur description, avec basculement vers npm-cache[.]com si nécessaire.
- Le malware s'auto-réplique en utilisant les tokens npm volés pour injecter le ver dans les autres paquets que chaque token peut publier, créant ainsi des infections de deuxième génération dans 400 autres paquets.
- Le ver infecte également les dépôts GitHub via des tokens GitHub App en modifiant .claude/settings.json et .vscode/tasks.json pour exécuter le payload lors de l'ouverture dans VS Code ou Claude.

## Discussion sur Hacker News (134 commentaires)

**Avis positifs** :
- Les gestionnaires de paquets (npm, yarn, pnpm) ont désactivé par défaut les scripts de préinstallation, ce qui constitue une première étape importante de mitigation
- Les séparations de workflows (build/test sans credentials, publication séparée avec credentials limités) et les cooldowns de version (5+ jours minimum) sont des défenses efficaces et peu coûteuses déjà disponibles
- GitHub et les registres npm auraient pu déployer des classifieurs automatiques ou des contrôles simples pour détecter et bloquer les repos de commande et contrôle (C2)
- La défense en profondeur (isolation du développement, permissions limitées, 2FA, signatures de packages) reste nécessaire et tout blocage de scripts install n'est qu'une étape parmi d'autres

**Avis négatifs** :
- Désactiver les scripts de préinstallation ne suffit pas : les attaquants peuvent facilement exécuter du code malveillant au moment de l'import (dans index.js) ou utiliser d'autres vecteurs comme les fichiers .vscode/tasks.json
- Les solutions proposées (cooldowns, séparation de workflows, audit) sont des demi-mesures qui ne résolvent pas le problème fondamental : npm exécute du code arbitraire par défaut depuis des milliers de petits mainteneurs non vérifiés
- La culture JavaScript d'installer des milliers de petites dépendances mises à jour rapidement crée une surface d'attaque bien plus large que d'autres écosystèmes (Debian, Python) avec audits différents
- Même avec provenance SLSA et attestations valides, le malware a été expédié : une clé GitHub compromise suffit car la provenance prouve juste quel commit a été construit, pas qu'il était autorisé
- Les outils de défense commerciaux restent peu efficaces et détectent principalement après coup ; npm/GitHub n'isolent pas rapidement les repos C2 ou n'arrêtent pas les vagues de propagation comme ils le devraient
