## Résumé de l'article

Oracle a instauré une interdiction stricte du code généré par l'IA dans les contributions au projet OpenJDK (plateforme open-source de développement Java), justifiant cette décision par des risques de sécurité, de conformité et de propriété intellectuelle. Cette politique contraste avec les pratiques internes d'Oracle, où les dirigeants affirment que l'IA génère déjà une part significative du code de l'entreprise.

- Les développeurs peuvent utiliser les modèles de langage (LLM) à titre privé pour le débogage et la révision de code, mais ne peuvent pas soumettre de code généré par l'IA aux dépôts ou demandes de pull du projet
- Le co-fondateur Larry Ellison a récemment déclaré que les modèles d'IA écrivaient désormais le code d'Oracle, tandis que le co-PDG Mike Sicilia a crédité les outils d'IA de permettre aux petites équipes d'ingénierie de livrer plus vite
- Oracle investit 70 milliards de dollars cette année dans l'expansion de ses centres de données, ce qui a conduit l'agence de notation S&P à abaisser sa note de crédit à BBB-, un cran au-dessus du statut de poubelle, en raison de l'incertitude des retours sur investissement

## Discussion sur Hacker News (147 commentaires)

**Avis positifs** :
- Oracle a raison de se protéger : Java est un logiciel mature critique pour de nombreuses entreprises, et accepter du code AI sans vérification rigoureux pose des risques de qualité, de maintenabilité et de responsabilité légale réels.
- La politique reflète des préoccupations légitimes autour des droits d'auteur et des licences : le code AI généré soulève des questions non résolues sur la provenance des données d'entraînement et les violations potentielles de propriété intellectuelle, ce qui est particulièrement pertinent pour un projet sous GPL.
- Le code AI tend à produire du « slop » : contributions volumineuses sans compréhension réelle, surcharge de travail pour les reviewers, code non maintenable, et incidents concrets (fuites de credentials, données corrompues, hallucinations). Le refus d'en accepter est pragmatique.
- La politique est renforcée par un cadre social existant : contrairement à GitHub où n'importe qui peut contribuer anonymement, des projets comme Linux ont maintenu des processus sociaux de vérification (apprentissage progressif, discussions IRC) qui les rendent moins vulnérables aux contributions de masse.
- L'ironie souligne un doute structurel : même Oracle, qui investit massivement dans l'IA, reconnaît implicitement que le code généré pose des problèmes quand il faut vraiment compter sur la qualité et la responsabilité.

**Avis négatifs** :
- Hypocrisie flagrante : Oracle promeut agressivement l'IA en interne et externement, mais refuse les contributions AI externes — « AI pour les peons, pas pour nous ». C'est une contradiction commerciale et éthique majeure.
- Impossibilité pratique d'application : impossible de détecter fiablement le code AI-généré, surtout s'il est remanié ou transformé par un humain. La politique repose sur l'autodéclaration volontaire, rendant son exécution illusoire.
- Raison réelle probablement légale, pas qualitative : la vraie motivation est la protection contre les poursuites en cas de violations de copyright, non la qualité du code. Oracle cache le problème derrière la rhétorique de la charge de review.
- Double standard avec implications systémiques : les problèmes que Oracle refuse externement (hallucinations, manque de compréhension, intégration fragile) affectent aussi son infrastructure interne, mais ceux-ci restent cachés. Cela montre que la politique ne résout rien, elle évite juste la visibilité.
- Contradiction avec le modèle SaaS : si Oracle refuse de dépendre du code AI sur OpenJDK, comment justifie-t-elle ses data centres construits pour entraîner les LLM, ses paris sur OpenAI, et son endettement croissant lié à l'IA ? C'est un aveu involontaire que le ROI AI n'est pas au rendez-vous.
