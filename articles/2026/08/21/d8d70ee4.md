## Résumé de l'article

Huzzah est un éditeur expérimental proposant une alternative aux agents de codage par IA. Au lieu de rédiger des prompts en langage naturel et impératif qui disparaissent après chaque interaction, l'utilisateur écrit du pseudocode déclaratif dans des fichiers persistants que l'éditeur convertit automatiquement en code réel, en capturant les modifications comme diffs pour guider le LLM.

- Le pseudocode remplace les longs prompts en langage naturel : plus concis, lisible, et engageant car l'utilisateur conçoit véritablement la structure du code
- Les fichiers .hz conservent une trace durable de l'intention humaine, contrairement aux prompts éphémères qui sont supprimés après leur utilisation
- Les modifications ultérieures génèrent automatiquement des diffs qui servent de prompts au modèle, réduisant la redondance et la consommation de tokens
- Le pseudocode peut servir de documentation pour les développeurs et permettre la génération de code pour plusieurs langages à partir d'une seule source
- L'approche fonctionne mieux pour les nouveaux projets et ne gère pas aisément les dépendances entre fichiers ou les domaines complexes

## Discussion sur Hacker News (136 commentaires)

**Avis positifs** :
- L'idée de persister l'intention humaine aux côtés du code généré est précieuse pour maintenir une source de vérité claire et tracer chaque ligne de code à son intent original.
- Utiliser du pseudocode structuré plutôt que des prompts discursifs réduit la fatigue cognitive et ramène une forme de méditation proche de la programmation traditionnelle.
- La source map automatique entre pseudocode et code généré résout un vrai problème : comprendre pourquoi et comment une section de code a été créée dans les grandes codebases.
- C'est une évolution plus pragmatique que le BDD ou les specs formelles, qui ne restent jamais à jour face au code réel et génèrent des murs de texte inutiles.
- Le concept de DSL ad-hoc sans syntaxe rigide exploite bien la flexibilité des LLMs, contrairement aux langages de programmation traditionnels conçus pour les compilateurs.

**Avis négatifs** :
- Persister le pseudocode c'est réinventer les commit messages, les ADRs et la documentation — des pratiques connues depuis longtemps que les équipes matures utilisent déjà.
- À grande échelle, maintenir un « jumeau pseudocode » du codebase entier devient une surcharge importante sans preuve que cela accélère réellement le développement.
- Si le pseudocode est imprécis, le LLM prend des décisions que vous ne contrôlez pas ; s'il est précis, vous écrivez presque du vrai code, perdant l'avantage de déléguer.
- Le système ne capture pas le bénéfice clé des agents : leur capacité à explorer l'architecture, suggérer des améliorations et brainstormer des solutions alternatives avec vous.
- Ajouter une nouvelle interface et un nouvel outil crée une friction d'adoption alors que les mêmes bénéfices (pseudocode + sourcemaps) peuvent être obtenus avec un simple prompt dans n'importe quel IDE existant.
