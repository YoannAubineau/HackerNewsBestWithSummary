## Résumé de l'article

HTML over WebSockets est une approche d'architecture web où le serveur envoie du HTML prérendu au client via une connexion WebSocket persistante, plutôt que du JSON. Le client place simplement le HTML reçu à l'endroit approprié, tandis que toute la logique de rendu reste sur le serveur dans un seul langage, sans API contractuelle.

- La méthode repose sur une connexion bidirectionnelle permanente (WebSocket) permettant au serveur d'envoyer du HTML assemblé et même de pousser des changements sans requête client
- Les avantages incluent : un seul moteur de rendu, pas d'API à maintenir, état conservé sur le serveur, latence réduite, capacités de diffusion temps réel, et très peu de JavaScript nécessaire côté client
- Les inconvénients sont : consommation mémoire serveur accrue (nécessite un état par client connecté), dégradation avec forte latence physique, non-fonctionnel hors ligne, et courbe d'apprentissage plus raide
- Des frameworks comme Phoenix LiveView (Elixir), Django Channels, Laravel Reverb et Blazor offrent des implémentations de ce pattern
- Server-Sent Events (SSE) constituent une alternative plus légère pour les cas où seul le serveur pousse des données (notifications, tableaux de bord) sans nécessiter la bidirectionnalité

## Discussion sur Hacker News (175 commentaires)

**Avis positifs** :
- Approche pragmatique et efficace pour les applications interne/B2B : 90% des bénéfices d'une SPA avec 10% du code, sans API à concevoir, sans duplication d'état entre DB et navigateur
- Modèle de programmation plus simple pour les mises à jour partielles : frameworks comme Turbo (Rails) et htmx permettent des mises à jour ciblées en quelques lignes de code (broadcast, turbo_frame)
- Sécurité renforcée contre l'injection XSS : le serveur échappe le HTML avant l'envoi, rendant les tentatives d'injection inoffensives côté client
- Redécouverte bienvenue d'une approche oubliée : après des années de complexité SPA, SSR avec WebSocket offre une alternative viable et plus maintenable pour beaucoup de cas d'usage
- Réduction massive du JavaScript et de la complexité client : moins de dépendances, moins de surface d'attaque, meilleure performance initiale

**Avis négatifs** :
- Statefulité par connexion crée des problèmes opérationnels : reconnexions, perte de session, clustering/load-balancing compliqués, monitoring difficile des ruptures de connexion
- Limitation sévère pour les cas hautement interactifs/réactifs : la dépendance graphique de réactivité doit être maintenue manuellement, inadapté pour les B2C complexes, jeux ou dashboards temps-réel
- Fausses économies : SSE suffit pour la plupart des cas (one-way push), HTTP/2 multiplex les connexions, WebSocket n'apporte aucun avantage latence en pratique pour les clics utilisateur
- Perte de découplage architectural fondamental : réintroduit le couplage serveur-client, complique les tests, le déploiement indépendant et la scalabilité horizontale contrairement à REST
- Problèmes non résolus d'état client : préservation du focus, position de scroll, sélection utilisateur restent complexes même avec les meilleures librairies (idiomorph), ajoutant du plumbing significatif
